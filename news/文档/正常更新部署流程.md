# 正常更新部署流程

## 🖥️ 生产环境如何打开 1Panel（SSL 续期必做）

生产 HTTPS 证书由 **1Panel** 签发/续期。新闻站 Nginx（`newsapp-nginx`）读的是项目里的副本：`/opt/newsapp/news/deploy/ssl/`。  
**1Panel 续期成功 ≠ 网站立刻生效**，必须把新证书同步进 `deploy/ssl/` 并重启 nginx。日常更新、证书告警、浏览器提示「不安全」时都走本节。

### 先分清两个地址

| 用途 | 地址 | 说明 |
|------|------|------|
| 新闻站（业务） | `https://news.gf-dsai.com` | 用户访问的站点，**不是** 1Panel |
| 落地页 | `https://aileading.gf-dsai.com` | 同样走 Docker Nginx + 证书副本 |
| **1Panel 管理面板** | `http(s)://119.3.127.211:<端口>/<安全入口>` | 服务器管理后台，**必须带端口和安全入口** |

生产机公网 IP：`119.3.127.211`（`news.gf-dsai.com` 解析到此）。

### 打开方式（推荐：浏览器）

1Panel **不是** SSH / FinalShell 里的桌面程序，要在本机浏览器打开。

1. SSH 登录生产机后执行（会打印面板地址、端口、安全入口、用户名）：

   ```bash
   sudo 1pctl user-info
   ```

   若提示找不到命令：

   ```bash
   sudo /usr/bin/1pctl user-info
   # 或
   sudo /usr/local/bin/1pctl user-info
   ```

2. 把输出里的地址整段复制到浏览器。完整形态类似：

   ```text
   http://119.3.127.211:xxxxx/xxxxxxxx
   https://119.3.127.211:xxxxx/xxxxxxxx
   ```

   - `xxxxx` 是面板端口（安装时随机，**不是** 80/443，也**不要**猜 `10086`）
   - 末尾路径是**安全入口**，漏写会 404 / 空白
   - 账号密码以 `1pctl user-info` 和安装时记录为准，**不要写进仓库**

3. 打不开时按顺序查：

   ```bash
   # 面板进程是否在跑
   sudo systemctl status 1panel

   # 本机是否在监听面板端口（把 1pctl 打出的端口填进去）
   sudo ss -lntp | grep -E '1panel|1p '

   # 云安全组 / 防火墙是否放行该端口（入站 TCP）
   sudo ufw status
   ```

   华为云 / 安全组未放行面板端口时，本机 curl 通、外网浏览器不通。

### 忘记密码或入口

```bash
sudo 1pctl user-info              # 查地址 / 端口 / 入口 / 用户名
sudo 1pctl update password        # 重置面板密码（按提示输入）
sudo 1pctl update entrance        # 重置安全入口（少用）
```

老版本命令可能是 `1pctl reset-password` / `1pctl port`，以 `sudo 1pctl -h` 为准。

### 场景：更新 / 续期 SSL 证书后必须同步到 Docker Nginx

证书在 1Panel 里续期后，**新闻站仍可能继续用旧 pem**，直到副本更新并重启 nginx。

**何时做：**

- 浏览器访问 `https://news.gf-dsai.com` 提示证书过期 / 不安全
- 1Panel 证书页显示即将过期或已自动续期
- 刚改过域名、重签证书，或 `aileading.gf-dsai.com` 证书也变了

**步骤：**

1. 按上一节打开 1Panel → **网站** → **证书**（或 **SSL**）
2. 找到 `news.gf-dsai.com`（落地页则再看 `aileading.gf-dsai.com`）
3. 确认状态为正常；过期则在面板里续期 / 重新申请
4. 在生产机同步到 Docker 使用的目录（优先脚本，找不到路径再手动）：

   ```bash
   cd /opt/newsapp/news

   # 推荐：自动从 1Panel 目录拷到 deploy/ssl/
   bash deploy/setup-1panel-ssl.sh news.gf-dsai.com

   # 落地页证书文件名不同，需单独拷成：
   # deploy/ssl/aileading-fullchain.pem
   # deploy/ssl/aileading-privkey.pem
   ```

   或手动（路径以 1Panel「证书详情 / nginx 配置」里的 `ssl_certificate` 为准）：

   ```bash
   cd /opt/newsapp/news
   mkdir -p deploy/ssl

   # 把下面 CERT_PATH 换成 1pctl / 面板里看到的真实目录
   CERT_PATH="/opt/1panel/certs/news.gf-dsai.com"
   sudo cp "$CERT_PATH"/fullchain.pem deploy/ssl/fullchain.pem 2>/dev/null \
     || sudo cp "$CERT_PATH"/cert.pem deploy/ssl/fullchain.pem
   sudo cp "$CERT_PATH"/privkey.pem deploy/ssl/privkey.pem 2>/dev/null \
     || sudo cp "$CERT_PATH"/key.pem deploy/ssl/privkey.pem

   sudo chmod 644 deploy/ssl/fullchain.pem
   sudo chmod 600 deploy/ssl/privkey.pem
   ```

5. 重启 nginx 使容器重新读证书：

   ```bash
   cd /opt/newsapp/news
   docker compose restart nginx
   docker compose exec nginx nginx -t
   docker compose logs nginx --tail 30
   ```

6. 验收：

   ```bash
   echo | openssl s_client -servername news.gf-dsai.com -connect 127.0.0.1:443 2>/dev/null \
     | openssl x509 -noout -dates -subject
   curl -sSI https://news.gf-dsai.com | head -8
   ```

   浏览器无痕窗口打开 `https://news.gf-dsai.com`，锁图标应正常，有效期应是新证书。

更细的证书定位见：`部署相关/1Panel证书定位和配置步骤.md`、`部署相关/1Panel-SSL证书配置指南.md`。  
容器/网站管理见：`部署相关/1Panel集成管理指南.md`。

### 场景2: 只更新了前端代码（client / client-h5）

**前端需要重新构建并复制到 volume：**  
PC 产物在 volume 根目录；H5 产物在同 volume 的 **`h5/`** 子目录（对应 Nginx `location /h5/`）。

#### 方法1: 从本地上传构建文件（推荐，最快）

**在本地：**

```powershell
# 1. 构建前端
cd E:\USER\SUREAL\Desktop\equity_news\news\client
npm run build

# 2. 使用 WinSCP 将 dist 目录上传到服务器 /tmp/dist
```

**在服务器：**

```bash
cd /opt/newsapp/news

# 1. 复制到 volume
VOLUME_PATH=$(docker volume inspect news_app_frontend | grep -i "Mountpoint" | awk '{print $2}' | tr -d '",')
sudo rm -rf "$VOLUME_PATH"/*
sudo cp -r /tmp/dist/* "$VOLUME_PATH/"

# 2. 重启 nginx
docker compose restart nginx

# 3. 验证
docker compose exec nginx stat -c%s /usr/share/nginx/html/index.html
```



#### 方法2: 在服务器上构建（推荐，如果服务器有 Node.js）

> 含 **PC（`client`）** 与 **H5（`client-h5`）**。勿把本机 Windows 的 `node_modules` 同步到服务器；若出现 `vite: Permission denied`，先 `rm -rf node_modules` 再 `npm install`。

**使用脚本（会清空整个前端 volume，含已部署的 `h5/`）：**

```bash
cd /opt/newsapp/news
chmod +x deploy/在服务器上构建前端.sh
bash deploy/在服务器上构建前端.sh
# 脚本只构建 client，且会 rm -rf volume 下全部文件（含 h5/）
# 只改 PC、要保留已部署的 H5：不要用本脚本，改走下方「仅更新 PC」
# 本次 PC 和 H5 都要更新：脚本跑完后，再执行下方「仅更新 H5」把 h5/ 拷回去
```

**或手动执行（PC + H5）：**

```bash
cd /opt/newsapp/news

# 1. 检查 Node.js（如果没有需要先安装）
node --version || echo "需要安装 Node.js"

# 2. 构建 PC 前端
cd client
# 代码/package.json 有更新时必须先装依赖（含 vite 等 devDependencies）
# 不要用 npm install --production，否则构建工具装不上
npm install
npm run build
cd ..

# 3. 构建 H5 前端（产物将放到 volume 的 h5/ 子目录）
cd client-h5
# 若 node_modules 来自 Windows 同步或报 vite: Permission denied：
#   rm -rf node_modules && npm install
npm install
npm run build
cd ..

# 4. 复制到 volume（先停共用该 volume 的容器，再清空拷贝，避免旧 assets 残留）
VOLUME_PATH=$(docker volume inspect news_app_frontend | grep -i "Mountpoint" | awk '{print $2}' | tr -d '",')
docker compose stop nginx app
sudo rm -rf "$VOLUME_PATH/assets" "$VOLUME_PATH/index.html" "$VOLUME_PATH/h5" "$VOLUME_PATH"/*
sudo mkdir -p "$VOLUME_PATH/h5"
sudo cp -a client/dist/. "$VOLUME_PATH/"
sudo cp -a client-h5/dist/. "$VOLUME_PATH/h5/"
# 核对：PC / H5 两侧 assets 数量应与 dist 一致（不应上百个旧文件）
echo "pc dist=$(ls client/dist/assets | wc -l) volume=$(sudo ls "$VOLUME_PATH/assets" | wc -l)"
echo "h5 dist=$(ls client-h5/dist/assets | wc -l) volume=$(sudo ls "$VOLUME_PATH/h5/assets" | wc -l)"

# 5. 启动容器（nginx 提供 / 与 /h5/）
docker compose start app
docker compose start nginx

# 6. 验证
docker compose exec nginx stat -c%s /usr/share/nginx/html/index.html
docker compose exec nginx stat -c%s /usr/share/nginx/html/h5/index.html
```

**仅更新 PC（未改 H5）时手动执行（只覆盖站点根目录，保留 volume 里的 `h5/`）：**

```bash
cd /opt/newsapp/news

# 1. 检查 Node.js（如果没有需要先安装）
node --version || echo "需要安装 Node.js"

# 2. 只构建 PC 前端
cd client
# 代码/package.json 有更新时必须先装依赖（含 vite 等 devDependencies）
# 不要用 npm install --production，否则构建工具装不上
# 若 node_modules 来自 Windows 同步或报 vite: Permission denied：
#   rm -rf node_modules && npm install
npm install
npm run build
cd ..

# 3. 只替换 volume 根目录的 PC 文件，不要删 h5/
VOLUME_PATH=$(docker volume inspect news_app_frontend | grep -i "Mountpoint" | awk '{print $2}' | tr -d '",')
docker compose stop nginx
sudo find "$VOLUME_PATH" -mindepth 1 -maxdepth 1 ! -name h5 -exec rm -rf {} +
sudo cp -a client/dist/. "$VOLUME_PATH/"
echo "pc dist=$(ls client/dist/assets | wc -l) volume=$(sudo ls "$VOLUME_PATH/assets" | wc -l)"
# h5 应仍在
sudo test -f "$VOLUME_PATH/h5/index.html" && echo "h5 kept" || echo "h5 missing"

# 4. 启动 nginx 并验证 PC（不要动 app）
docker compose start nginx
docker compose exec nginx stat -c%s /usr/share/nginx/html/index.html
docker compose exec nginx stat -c%s /usr/share/nginx/html/h5/index.html
```

**仅更新 H5（未改 PC）时可跳过 PC 构建，但仍建议先 `docker compose stop nginx`，再只覆盖 `h5/`：**

```bash
cd /opt/newsapp/news/client-h5
npm install && npm run build
cd ..
VOLUME_PATH=$(docker volume inspect news_app_frontend | grep -i "Mountpoint" | awk '{print $2}' | tr -d '",')
docker compose stop nginx
sudo rm -rf "$VOLUME_PATH/h5"
sudo mkdir -p "$VOLUME_PATH/h5"
sudo cp -a client-h5/dist/. "$VOLUME_PATH/h5/"
docker compose start nginx
```

### 场景4: 私有公众号专队（we-mp-rss，替代 wewe-rss）

> **产品说明（名单 / 协作 / 映射）**：[需求说明/私有公众号专队与we-mp-rss说明.md](./需求说明/私有公众号专队与we-mp-rss说明.md)  
> **本地采集端**：[deploy/we-mp-rss/README.md](../deploy/we-mp-rss/README.md)  
> 旧 wewe-rss 中转 `PLATFORM_URL` 已失效；生产请用 **we-mp-rss**（默认端口 **8001**）。与 `app` **并列容器**，不是 Docker-in-Docker。

#### 4.0 架构

| 做法 | 结论 |
|------|------|
| 把 we-mp-rss **打进**新闻 `app` 镜像 | **否** |
| Docker-in-Docker（app 里再起 docker） | **否** |
| 主 `docker-compose.yml` 并列 `we-mp-rss`（同 `newsapp-network`） | **生产推荐** |
| 仅 `deploy/we-mp-rss/docker-compose.yml` 单独 `up` | 本地/临时可用；与主 compose **网络可能不同**，Base URL 勿照搬服务名 |

专队名单：**舆情监控对象（有企业公众号 id）+ 第三方公众号** → 页面「从监控同步」。新榜「数据不存在」**不再**自动进出队。

#### 4.1 同步到生产的内容

| 同步 | 不同步 |
|------|--------|
| `news/server/**`、`news/client` 构建产物 | 本地 `.env` 原样拷密钥 |
| `news/docker-compose.yml`（含 `we-mp-rss` 服务） | `deploy/we-mp-rss/data/*`（会话/库在云上生成） |
| `news/deploy/we-mp-rss/**`（compose / README / `.env.example` / `data/.gitkeep`） | we-mp-rss 内 `*.db`、`.secret_key`、`*.lic` |
| 云上 `.env` 增补 `MP_RSS_*`（见 4.2） | 中文占位密码 |

#### 4.2 生产 `news/.env`

```env
# ---------- we-mp-rss（私有公众号专队，推荐）----------
MP_RSS_PROVIDER=werss
# 主 compose 同网：用服务名（不要写 127.0.0.1，那是 app 容器自己）
MP_RSS_BASE_URL=http://we-mp-rss:8001
MP_RSS_USERNAME=admin
MP_RSS_PASSWORD=请换成强密码
# MP_RSS_HOST_BIND=127.0.0.1
# MP_RSS_HOST_PORT=8001

# 催登活码外链（新闻公网地址）
NEWS_PUBLIC_BASE_URL=https://你的新闻域名
WEWE_LIVE_QR_SECRET=请换成强随机串
WEWE_LIVE_QR_TTL_HOURS=48
```

页面：管理员设置 → **私有公众号采集** → 采集后端选 **we-mp-rss**，Base URL 与上一致（服务端用）；浏览器「we-mp-rss 管理」走本站 **`https://新闻域名/we-mp-rss/`**（nginx 反代，勿用 `we-mp-rss:8001`）。运维邮优先填页面 `ops_email`。

改完 `.env`：

```bash
cd /opt/newsapp/news
docker compose up -d we-mp-rss
docker compose up -d --force-recreate app
```

#### 4.3 启动 we-mp-rss

**方式 A — 生产推荐（主 compose）**

```bash
cd /opt/newsapp/news
docker compose pull we-mp-rss
docker compose up -d we-mp-rss
```

- 服务名 `we-mp-rss`，容器名多为 `newsapp-we-mp-rss`
- `.env`：`MP_RSS_BASE_URL=http://we-mp-rss:8001`

**方式 B — 单独目录（本地/临时）**

```bash
cd /opt/newsapp/news/deploy/we-mp-rss
cp .env.example .env   # 改密码
docker compose up -d
```

- 若与 `newsapp-network` 不通，app 侧 Base URL 改宿主机可达地址（如 `http://172.17.0.1:8001`），**不要**写服务名。

验证：

```bash
curl -sS -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8001/
docker compose -f /opt/newsapp/news/docker-compose.yml exec app \
  node -e "require('http').get(process.env.MP_RSS_BASE_URL||'http://we-mp-rss:8001/',r=>console.log(r.statusCode)).on('error',e=>console.error(e.message))"
```

#### 4.4 清理旧 wewe-rss（可选）

确认专队已切 `werss` 且 we-mp-rss 正常后：

```bash
cd /opt/newsapp/news
docker compose stop wewe-rss
docker compose rm -f wewe-rss
# 避免再次 up 拉起：docker compose up -d --scale wewe-rss=0
# 可选删数据：rm -rf deploy/wewe-rss/data/*（不可恢复）
```

可注释 `.env` 中 `WEWE_RSS_BASE_URL` / `WEWE_RSS_AUTH_CODE` / `WEWE_PLATFORM_URL`；**保留** `NEWS_PUBLIC_BASE_URL`、`WEWE_LIVE_QR_SECRET`（催登活码仍可能用）。**不要**删 MySQL 里 `wewe_private_*` 专队表。

#### 4.5 代码更新后拉起

```bash
cd /opt/newsapp/news
# 同步 server、前端 dist、docker-compose.yml、deploy/we-mp-rss/
docker compose up -d we-mp-rss
docker compose up -d --force-recreate app
docker compose ps
docker compose logs we-mp-rss --tail 30
docker compose logs app --tail 30
```

#### 4.6 上线验收

1. we-mp-rss HTTP 200；管理页完成**微信读书**扫码/Cookie  
2. 新闻站 → 管理员设置 → **私有公众号采集**  
   - 采集后端 = we-mp-rss，Base URL 正确；探测可达  
3. **专队账号 →「从监控同步」** → 待订阅「粘贴链接」映射 `MP_WXS_*`  
4. 分步开：总开关 → 提取 / 入库 → 催办  
5. 确认提取有暂存；入库默认吃 **≤ 昨天** 业务日（当天数据次日凌晨或强制入库）

#### 4.7 常见错误

| 现象 | 处理 |
|------|------|
| `ECONNREFUSED 127.0.0.1:8001` | we-mp-rss 未起，或 app 误配本机地址（容器内应写 `http://we-mp-rss:8001`） |
| 浏览器打开 `we-mp-rss:8001` DNS 失败 / 管理页 iframe 空白 | 属正常：Docker 内网名不能给浏览器用。部署后访问本站 **`/we-mp-rss/`**；nginx 需能解析 `we-mp-rss`（同网或 `docker network connect news_newsapp-network we-mp-rss`）后 `docker compose exec nginx nginx -s reload` |
| 管理页壳子出来但控制台 `/api/v1/wx/...` 404 | we-mp-rss 按根路径调 API；nginx 须在通用 `/api` **之前**有 `location ^~ /api/v1/` 反代到 we-mp-rss，然后 reload |
| `/we-mp-rss/` 顶栏有、中间空白 | Vue 不支持子路径。请用 **`https://新闻域名:8443/`**（nginx 独立入口，compose 映射 `MP_RSS_UI_PORT`）；安全组放行 8443 |
| 粘贴链接失败 / 映射非 `MP_WXS_*` | 看 we-mp-rss 日志；确认 by_article 返回 `mp_id`/`biz`，不是文章 id |
| 管理页有文但 `news_detail` 无 | we-mp-rss 库 ≠ 新闻库；查暂存表与入库业务日（≤ 昨天） |
| 催登邮件仍写「wewe」 | 文案遗留；`collector_provider=werss` 时实际走 we-mp-rss 二维码 |
| 旧 wewe 活码 / PLATFORM 502 | 已废弃；改 we-mp-rss，勿再依赖 weread.111965.xyz |

## 📝 重要说明



### 1. 后端代码（server目录）

- ✅ **自动同步**：通过 volume 挂载 `./server:/app/server`
- ✅ **无需重建镜像**：代码更改后只需重启容器
- ✅ **即时生效**：重启后立即生效



### 2. 前端代码（client / client-h5）

- ⚠️ **需要构建**：PC 在 `client` 执行 `npm run build`；H5 在 `client-h5` 执行 `npm run build`
- ⚠️ **需要复制到 volume**：PC → `app_frontend` 根目录；H5 → 同 volume 的 **`h5/`** 子目录（Nginx `location /h5/`）
- ⚠️ **需要重启 nginx**：复制后需要重启（或 stop/start）nginx 容器
- ⚠️ **勿同步 Windows `node_modules`**：在服务器上 `npm install`；若 `vite: Permission denied`，先删 `node_modules` 再重装



### 3. 数据库变更

- 如果修改了数据库结构，需要手动执行 SQL 迁移
- 或者通过应用启动时的自动创建逻辑（如果实现了）
- **应用维度与匹配规则**（`applications.id` ↔ `data_app_id`、上市进展底层匹配、新闻舆情被投企业过滤、被投企业列表/导出等）已整理为说明文档：`需求说明/数据应用隔离与业务匹配说明.md`。部署后若列表为空或匹配异常，请先核对 `applications` 中是否存在「新闻舆情」「上市进展」等应用记录，以及业务表 `data_app_id` 是否已回填。



### 4. SSL 证书（1Panel）

- 证书在 **1Panel** 管理，打开方式见文首「生产环境如何打开 1Panel」
- Docker Nginx 用的是 `deploy/ssl/fullchain.pem` + `privkey.pem`（落地页另有 `aileading-*.pem`）
- 面板里续期后必须再拷贝 + `docker compose restart nginx`，否则站点仍用旧证

### Q: 竞品分析跑批中途重启了 Docker / app，会怎样？如何处理？

**影响说明**

竞品分析在 `app` 容器内用 `setImmediate` 异步执行，**不是**持久化队列。重启 `app`（或整机 / Docker Desktop）会：

- 立刻中断当前跑批，**不会自动续跑**
- 库里的运行记录常会停在 `running` / `queued`（不会自动变 `failed`）
- 同一主体再点「竞品分析」可能被 **409** 拒绝（已有运行中任务）
- 竞品明细落库在最后且走事务，中途挂掉一般**不会半截写入**；多数仍是上一版结果

**注意**：排查时不要用 `docker compose exec app node -e "require('./db')"`（工作目录是 `/app`，模块在 `/app/server`）。查库优先走 **mysql 容器**，或加 `-w /app/server`。

**1. 先查卡住的运行（投前 + 投后）**

在服务器 `/opt/newsapp/news` 下执行（账号密码以 `.env` 的 `DB_USER` / `DB_PASSWORD` / `DB_NAME` 为准；下文为 compose 默认示例）：

```bash
cd /opt/newsapp/news

docker compose exec -T mysql mysql -unewsapp -p'NewsApp@2024' investment_tools -e "
-- 所有卡住的投后跑批
SELECT F_Id, status, message, started_at, finished_at, invested_enterprise_id
FROM sourcing_competitor_run
WHERE F_DeleteMark=0 AND status IN ('running','queued')
ORDER BY F_CreatorTime DESC
LIMIT 20;

-- 所有卡住的投前跑批
SELECT F_Id, status, message, started_at, finished_at, pre_investment_project_id
FROM sourcing_pre_investment_competitor_run
WHERE F_DeleteMark=0 AND status IN ('running','queued')
ORDER BY F_CreatorTime DESC
LIMIT 20;
"
```

**示例（2026-07-27 实操）**：中途重启后查到投前卡住：


| F_Id                | status  | started_at          | pre_investment_project_id |

### 港交所 iFinD 数据同步说明

**功能说明：**

- 港交所上市申请数据可通过同花顺 iFinD 接口获取
- **Windows 本地环境**：使用本地 iFinDPy SDK + 用户名/密码登录
- **Linux 生产环境**：使用 HTTP API + refresh_token 获取 access_token

**架构对比：**


| 环境           | 认证方式                         | 数据获取方式           | SDK 安装          |
| ------------ | ---------------------------- | ---------------- | --------------- |
| Windows      | 用户名+密码 或 refresh_token       | 本地 iFinDPy SDK   | 手动下载安装          |
| Linux/Docker | refresh_token → access_token | HTTP RESTful API | Dockerfile 自动安装 |


**Windows 环境配置步骤：**

1. 从同花顺官网下载 Windows 版 iFinD SDK
2. 解压到 `THSDataInterface_Windows/` 目录
3. 运行 `python installiFinDPy.py` 安装
4. 打开 iFinD 终端 → 「超级命令」→「工具」→「refresh_token 查询」获取 token
5. 在「系统设置 → 上市数据配置」中填写用户名、密码或 refresh_token

**Linux/Docker 环境配置步骤：**

1. SDK 已在 Dockerfile 中配置自动安装
2. 使用 Windows 环境获取的 refresh_token
3. 在管理后台配置页面填入 Token
4. 系统自动通过 HTTP API 获取数据

**详细文档：**

- [iFinD 集成详细说明](./iFinD集成说明.md)
- [生产环境更新指南 - iFinD 配置](./生产环境更新指南.md#-港交所-ifind-配置说明)

**Linux Docker 环境注意事项：**

1. **确保 Python 依赖已安装**
  ```bash

   docker compose exec app python3 -c "import pandas; print('OK')"

   # 如果报错，需要重新构建镜像

   docker compose up -d
  ```
2. **iFinD SDK 安装**
  - 同花顺 iFinD SDK 需要手动安装，不通过 PyPI 发布
  - Dockerfile 已配置自动安装 Linux 版 SDK
  - Windows 版 SDK 需单独下载，不包含在代码仓库中（已添加到 .gitignore）
3. **状态映射规则**

  | 日期匹配条件            | 系统状态     |
  | ----------------- | -------- |
  | 首次申请日期在区间内        | **递交A1** |
  | 通过聆讯日期在区间内        | **通过聆讯** |
  | 上市日期在区间内          | **上市**   |
  | 状态更新日期在区间内 + 终止状态 | 保持原状态    |

4. **常见错误排查**

### 何时需要完全重新构建

以下情况需要执行完全重新构建：

- ✅ 修改了 `Dockerfile`
- ✅ 修改了依赖文件（`package.json`、`package-lock.json`）
- ✅ 修改了前端代码并需要在镜像中构建
- ✅ 添加/删除了系统依赖
- ✅ **修改了 Python 依赖（**`requirements.txt`**）** ⬅️ 常见！
- ✅ 需要清理旧的镜像和构建缓存
- ✅ 迁移到新环境或全新部署

⚠️ **注意**：如果只是修改了后端业务代码（`server/`目录），不需要重新构建，只需重启容器即可（见场景1）。

⚠️ **Python 依赖特别说明**：

- Python 依赖在 Docker 镜像构建时安装（见 Dockerfile 第 73-79 行）

## 🔍 构建故障排查



### 问题1: 构建失败，提示内存不足

**解决方法：**

```bash
# 增加 Node.js 内存限制
docker compose build --build-arg NODE_OPTIONS="--max-old-space-size=6144"

# 或者增加 Docker 的内存限制（在 Docker Desktop 设置中）
```



### 问题2: 依赖下载失败

**解决方法：**

```bash
# 清理 npm 缓存
docker compose build --no-cache

# 或者修改 Dockerfile 中的镜像源（已配置国内源）
```



### 问题3: 构建速度慢

**解决方法：**

```bash
# 使用多核并行构建
DOCKER_BUILDKIT=1 docker compose build --no-cache --parallel

# 或者只重建有变化的服务
docker compose build --no-cache app
```



### 问题4: 启动后容器立即退出

**解决方法：**

```bash
# 查看详细日志
docker compose logs app

# 进入容器调试
docker compose run --rm app /bin/bash

# 检查环境变量
docker compose exec app env | grep DB_
```

## 📝 重新构建 vs 重启容器


| 操作   | 使用场景            | 数据影响 | 耗时        |
| ---- | --------------- | ---- | --------- |
| 重启容器 | 修改后端业务代码        | 保留数据 | 快（<1分钟）   |
| 更新前端 | 修改前端代码          | 保留数据 | 中等（2-5分钟） |
| 重新构建 | 修改依赖、Dockerfile | 保留数据 | 慢（5-20分钟） |
| 完全重建 | 全新环境、重置         | 删除数据 | 慢（5-20分钟） |
