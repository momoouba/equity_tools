# 正常更新部署流程

## 📋 更新前后端代码后的部署步骤

### 场景1: 只更新了后端代码（server目录）

**后端代码通过 volume 挂载，代码更改会自动同步，只需重启容器：**

```bash
cd /opt/newsapp/news

# 1. 重启应用容器（代码已自动同步）
docker compose restart app

# 2. 查看日志确认启动成功
docker compose logs -f app
```

**验证：**

```bash
# 检查容器状态
docker compose ps

# 测试健康检查
curl http://localhost:3001/api/health
```

### 场景2: 只更新了前端代码（client目录）

**前端需要重新构建并复制到 volume：**

#### 方法1: 从本地上传构建文件（推荐，最快）

**在本地：**

```powershell
# 1. 构建前端
cd E:\USER\SUREAL\Desktop\equity_news\news\client
npm run build

# 2. 使用 WinSCP 将 dist 目录上传到服务器 /tmp/dist
```

**在服务器：**

```bash
cd /opt/newsapp/news

# 1. 复制到 volume
VOLUME_PATH=$(docker volume inspect news_app_frontend | grep -i "Mountpoint" | awk '{print $2}' | tr -d '",')
sudo rm -rf "$VOLUME_PATH"/*
sudo cp -r /tmp/dist/* "$VOLUME_PATH/"

# 2. 重启 nginx
docker compose restart nginx

# 3. 验证
docker compose exec nginx stat -c%s /usr/share/nginx/html/index.html
```



#### 方法2: 在服务器上构建（推荐，如果服务器有 Node.js）

**使用脚本（推荐）：**

```bash
cd /opt/newsapp/news
chmod +x deploy/在服务器上构建前端.sh
bash deploy/在服务器上构建前端.sh
```

**或手动执行：**

```bash
cd /opt/newsapp/news

# 1. 检查 Node.js（如果没有需要先安装）
node --version || echo "需要安装 Node.js"

# 2. 构建前端
cd client
npm install  # 首次构建需要
npm run build
cd ..

# 3. 复制到 volume
VOLUME_PATH=$(docker volume inspect news_app_frontend | grep -i "Mountpoint" | awk '{print $2}' | tr -d '",')
sudo rm -rf "$VOLUME_PATH"/*
sudo cp -r client/dist/* "$VOLUME_PATH/"

# 4. 重启 nginx
docker compose restart nginx
```



#### 方法3: 在容器内构建（如果服务器没有 Node.js）

```bash
cd /opt/newsapp/news
chmod +x deploy/在容器内构建前端.sh
bash deploy/在容器内构建前端.sh
```

### 场景4: 首次/更新私有公众号 wewe（wewe-rss）



#### 4.0 架构（先看清再配）


| 做法                                                                       | 结论                                                               |
| ------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| 把 wewe **打进**新闻 `app` 镜像                                                 | **否**                                                            |
| Docker-in-Docker（app 里再起 docker）                                         | **否**                                                            |
| 主 `docker-compose.yml` 并列 `wewe-rss` **服务**（与 `app` 同 `newsapp-network`） | **生产推荐**                                                         |
| 仅 `deploy/wewe-rss/docker-compose.yml` 单独 `up`                           | 本地/临时可用；与主 compose **网络不同**，`.env` 的 `WEWE_RSS_BASE_URL` 不能照搬服务名 |


更细的说明：`deploy/wewe-rss/README.md`。

#### 4.1 需要同步到生产的内容（不要整机照搬本地）


| 同步                                                            | 不同步                                                      |
| ------------------------------------------------------------- | -------------------------------------------------------- |
| `news/server/**`（volume 挂载后 `restart app`）                    | 本地 `.env` 原样拷贝密钥                                         |
| `news/client` 构建后的 `dist` → 前端 volume                         | `node_modules`、临时探路脚本                                    |
| `news/docker-compose.yml`（含 wewe-rss 服务）                      | 未提交的实验改动                                                 |
| `news/deploy/wewe-rss/**`（compose / README / `data/.gitkeep`） | `deploy/wewe-rss/data/*.db`（会话库在云上生成；`*.db` 已 gitignore） |
| 云上 `/opt/newsapp/news/.env` **增补 wewe 段**（见下）                 | 中文占位符（如「运维邮箱」「强随机串」）                                     |




#### 4.2 生产 `news/.env` 怎么加

在服务器编辑 `/opt/newsapp/news/.env`（与 mysql/app 同一文件），建议增加：

```env
# ---------- wewe-rss（私有公众号专队）----------
# AUTH：必须与 wewe 容器内 AUTH_CODE 一致（主 compose 时同一变量注入两边）
WEWE_RSS_AUTH_CODE=请换成强随机串

# BASE_URL：取决于 wewe 怎么起（见 4.3），容器内互通时用服务名
WEWE_RSS_BASE_URL=http://wewe-rss:4000

# 4000 默认只绑本机，避免公网裸奔
WEWE_HOST_BIND=127.0.0.1
WEWE_HOST_PORT=4000

# 活码邮件 / 外链：填浏览器能打开的新闻公网地址（含协议；有端口要带端口）
NEWS_PUBLIC_BASE_URL=https://你的新闻域名或公网IP
WEWE_LIVE_QR_SECRET=请换成另一段强随机串
WEWE_LIVE_QR_TTL_HOURS=48

# wewe 自身外链根（直连管理页或生成链接时用；可与新闻公网一致）
WEWE_SERVER_ORIGIN_URL=https://你的新闻域名或公网IP

# 可选：PLATFORM 不通时换备用
# WEWE_PLATFORM_URL=https://weread.111965.xyz
# WEWE_PLATFORM_URL=https://weread.965111.xyz
```

**运维邮箱** `WEWE_OPS_EMAIL`**：**

- **优先读页面**：管理员设置 → 私有公众号 wewe → 专队配置 → `ops_email`
- 代码顺序：`页面 ops_email` → 没有才用环境变量 `WEWE_OPS_EMAIL`
- 页面已配置真实邮箱时：**不必**在 `.env` 写 `WEWE_OPS_EMAIL`；更不要留「运维邮箱」这类占位中文

改完 `.env` 后必须：

```bash
cd /opt/newsapp/news
docker compose up -d wewe-rss   # 或重启已有 wewe
docker compose up -d app        # 使 app 读到新环境变量（仅 restart 有时不够，建议 recreate）
# 若只改了 WEWE_* 且 compose 未改服务定义，也可用：
# docker compose up -d --force-recreate app wewe-rss
```



#### 4.3 `WEWE_RSS_BASE_URL` 与启动方式（易踩坑）

**方式 A — 生产推荐：主 compose 起 wewe**

```bash
cd /opt/newsapp/news
docker compose pull wewe-rss
docker compose up -d wewe-rss
```

- 容器名一般为 `newsapp-wewe-rss`，服务名 `wewe-rss`
- `.env`：`WEWE_RSS_BASE_URL=http://wewe-rss:4000`（**不要**写 `127.0.0.1`，那是 app 容器自己）
- `WEWE_RSS_AUTH_CODE` 同时作为 wewe 的 `AUTH_CODE`（见主 compose）

**方式 B — 临时：单独目录 compose（你已在用时）**

```bash
cd /opt/newsapp/news/deploy/wewe-rss
# 该目录 .env 里是 AUTH_CODE=...（注意变量名是 AUTH_CODE，不是 WEWE_RSS_AUTH_CODE）
docker compose up -d
```

- 网络通常是 `wewe-rss_default`，与新闻 `newsapp-network` **不是同一个**
- 此时新闻 `.env` 写 `http://wewe-rss:4000` **经常解析失败**
- 应改为宿主机可达地址，例如：
  - `WEWE_RSS_BASE_URL=http://172.17.0.1:4000`
  - 或 `http://host.docker.internal:4000`（视云主机 Docker 是否支持）
- 且 `WEWE_RSS_AUTH_CODE` 必须等于 `deploy/wewe-rss/.env` **的** `AUTH_CODE`

验证 app 能否访问 wewe：

```bash
# 宿主机
curl -sS -o /dev/null -w "%{http_code}\n" http://127.0.0.1:4000/

# 新闻容器内（方式 A 用服务名；方式 B 换成你配置的 BASE_URL）
docker compose -f /opt/newsapp/news/docker-compose.yml exec app \
  node -e "require('http').get(process.env.WEWE_RSS_BASE_URL||'http://wewe-rss:4000/',r=>console.log(r.statusCode)).on('error',e=>console.error(e.message))"
```



#### 4.4 前后端代码更新（含 wewe 功能时）

与场景 3 相同，并确保 compose / `.env` 已按 4.2～4.3 就绪：

```bash
cd /opt/newsapp/news
# 1) 同步 server、client 构建产物、docker-compose.yml、deploy/wewe-rss/
# 2) 前端覆盖 volume + restart nginx（见场景2/3）
# 3) wewe + app
docker compose up -d wewe-rss
docker compose up -d --force-recreate app
docker compose ps
docker compose logs wewe-rss --tail 30
docker compose logs app --tail 30
```



#### 4.5 上线后验收与分步开关

1. 宿主机 / 容器内探测 wewe HTTP 200  
2. **Nginx 必须把 wewe 路径反代到 `app`**（见 `deploy/nginx-site.conf`）：  
   `/wewe-rss-gate`、`/wewe-rss`、`/dash`、`/trpc`、`/wewe/`  
   若漏配，配置页「wewe-rss 管理」iframe 会空白（请求落到前端 `index.html`）。  
   更新 conf 后执行 `docker compose restart nginx`，再验证：
   ```bash
   curl -sSI https://news.gf-dsai.com/wewe-rss-gate | head -8
   # Content-Type 应为 text/html 且来自 Node gate，不应是前端壳长期无跳转
   curl -sS -o /dev/null -w "%{http_code}\n" https://news.gf-dsai.com/dash/
   ```
3. 打开新闻站 → 管理员设置 → **私有公众号 wewe**  
   - 「探测 wewe」可达  
   - **会话 / 读书账号 = 可用**（需活码或 wewe 管理页扫码；「可达」≠ 已登录）  
4. 专队配置填写 **`ops_email`**（若 `.env` 未配运维邮）  
5. **分步开开关**：总开关 + 允许入队 → 观察专队列表 → 再开提取 / 入库 / 催办  
6. 待订阅：在左侧 **「专队账号」** 粘贴分享链接（不是 wewe-rss 管理页）



#### 4.6 常见错误对照


| 现象                                         | 处理                                                                 |
| ------------------------------------------ | ------------------------------------------------------------------ |
| 「wewe-rss 管理」嵌入空白                          | Nginx 未反代 `/wewe-rss-gate` `/dash` `/trpc` → 更新 `nginx-site.conf` 并 `restart nginx` |
| 探测失败 / `ECONNREFUSED` / 容器内解析不到 `wewe-rss` | 检查 4.3：单独 up 时不要用服务名；或改回主 compose                                   |
| 「暂无可用读书账号」                                 | 扫码登录微信读书；页面看读书账号 status=1                                           |
| 活码一直二维码 / 红绿乱报                             | 用新版活码页；成功后回专队配置刷新会话                                                 |
| 催办无收件人                                     | 页面 `ops_email` 或 `.env` `WEWE_OPS_EMAIL` 至少一处为真实邮箱                  |
| AUTH 不对                                    | `WEWE_RSS_AUTH_CODE` 与 wewe `AUTH_CODE` 不一致                         |

## 📝 重要说明



### 1. 后端代码（server目录）

- ✅ **自动同步**：通过 volume 挂载 `./server:/app/server`
- ✅ **无需重建镜像**：代码更改后只需重启容器
- ✅ **即时生效**：重启后立即生效



### 2. 前端代码（client目录）

- ⚠️ **需要构建**：必须先运行 `npm run build`
- ⚠️ **需要复制到 volume**：构建后的文件需要复制到 `app_frontend` volume
- ⚠️ **需要重启 nginx**：复制后需要重启 nginx 容器



### 3. 数据库变更

- 如果修改了数据库结构，需要手动执行 SQL 迁移
- 或者通过应用启动时的自动创建逻辑（如果实现了）
- **应用维度与匹配规则**（`applications.id` ↔ `data_app_id`、上市进展底层匹配、新闻舆情被投企业过滤、被投企业列表/导出等）已整理为说明文档：`需求说明/数据应用隔离与业务匹配说明.md`。部署后若列表为空或匹配异常，请先核对 `applications` 中是否存在「新闻舆情」「上市进展」等应用记录，以及业务表 `data_app_id` 是否已回填。

### Q: 竞品分析跑批中途重启了 Docker / app，会怎样？如何处理？

**影响说明**

竞品分析在 `app` 容器内用 `setImmediate` 异步执行，**不是**持久化队列。重启 `app`（或整机 / Docker Desktop）会：

- 立刻中断当前跑批，**不会自动续跑**
- 库里的运行记录常会停在 `running` / `queued`（不会自动变 `failed`）
- 同一主体再点「竞品分析」可能被 **409** 拒绝（已有运行中任务）
- 竞品明细落库在最后且走事务，中途挂掉一般**不会半截写入**；多数仍是上一版结果

**注意**：排查时不要用 `docker compose exec app node -e "require('./db')"`（工作目录是 `/app`，模块在 `/app/server`）。查库优先走 **mysql 容器**，或加 `-w /app/server`。

**1. 先查卡住的运行（投前 + 投后）**

在服务器 `/opt/newsapp/news` 下执行（账号密码以 `.env` 的 `DB_USER` / `DB_PASSWORD` / `DB_NAME` 为准；下文为 compose 默认示例）：

```bash
cd /opt/newsapp/news

docker compose exec -T mysql mysql -unewsapp -p'NewsApp@2024' investment_tools -e "
-- 所有卡住的投后跑批
SELECT F_Id, status, message, started_at, finished_at, invested_enterprise_id
FROM sourcing_competitor_run
WHERE F_DeleteMark=0 AND status IN ('running','queued')
ORDER BY F_CreatorTime DESC
LIMIT 20;

-- 所有卡住的投前跑批
SELECT F_Id, status, message, started_at, finished_at, pre_investment_project_id
FROM sourcing_pre_investment_competitor_run
WHERE F_DeleteMark=0 AND status IN ('running','queued')
ORDER BY F_CreatorTime DESC
LIMIT 20;
"
```

**示例（2026-07-27 实操）**：中途重启后查到投前卡住：


| F_Id                | status  | started_at          | pre_investment_project_id |
| ------------------- | ------- | ------------------- | ------------------------- |
| 2026072721215600001 | running | 2026-07-27 21:21:56 | 2026072712212400001       |
| 2026062916534200001 | running | 2026-06-29 16:53:42 | 2026062614094200001       |


当天中断的是第一条；第二条为历史僵尸 `running`，建议一并清理。

**Linux/Docker 环境配置步骤：**

### 何时需要完全重新构建

以下情况需要执行完全重新构建：

- ✅ 修改了 `Dockerfile`
- ✅ 修改了依赖文件（`package.json`、`package-lock.json`）
- ✅ 修改了前端代码并需要在镜像中构建
- ✅ 添加/删除了系统依赖
- ✅ **修改了 Python 依赖（**`requirements.txt`**）** ⬅️ 常见！
- ✅ 需要清理旧的镜像和构建缓存
- ✅ 迁移到新环境或全新部署

⚠️ **注意**：如果只是修改了后端业务代码（`server/`目录），不需要重新构建，只需重启容器即可（见场景1）。

⚠️ **Python 依赖特别说明**：

- Python 依赖在 Docker 镜像构建时安装（见 Dockerfile 第 73-79 行）
- 新增 `.py` 文件如果使用了新依赖（如 `pandas`、`akshare`、`markitdown`），必须重新构建镜像
- 常见错误：`ModuleNotFoundError: No module named 'pandas'` → 需要重新构建镜像
- **BP 文件解析**依赖 `markitdown[all]`（Microsoft 开源文档转 Markdown 工具），修改后同样需要重建镜像

## 📝 重新构建 vs 重启容器


| 操作   | 使用场景            | 数据影响 | 耗时        |
| ---- | --------------- | ---- | --------- |
| 重启容器 | 修改后端业务代码        | 保留数据 | 快（<1分钟）   |
| 更新前端 | 修改前端代码          | 保留数据 | 中等（2-5分钟） |
| 重新构建 | 修改依赖、Dockerfile | 保留数据 | 慢（5-20分钟） |
| 完全重建 | 全新环境、重置         | 删除数据 | 慢（5-20分钟） |
