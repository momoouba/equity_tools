## 1. 目标与非目标

**目标**：手机上按权限**查看**系统里已经跑出来的结果；**地址与 PC 相同**，打开即是 H5 排版。

**非目标**：在手机上配置系统、运维专队、创建/改数据、管理分享链、做估值推演/竞品作业流；也不要求用户收藏单独的「手机站」域名或路径。

### 1.1 入口：同址自动进 H5（已按你的期望锁定）

**用户侧（期望）**

| 谁 | 打开什么 | 看到什么 |
|----|----------|----------|
| 手机浏览器 | 与 PC **相同**的站点地址（如 `https://news.xxx.com` 或书签里的登录/首页） | **自动**进入 H5 登录/只读壳（手机排版） |
| 电脑浏览器 | 同一地址 | 现有 PC 管理台（不变） |
| 任何人 | `/share/...` 等分享外链 | **仍是现有分享页**（不改成 H5 壳）。PC 移动端本就不展示分享按钮 → **无需求**做分享移动专项 |

**实现侧（对用户透明）**

- H5 工程仍独立构建，资源挂在同域 **`/h5/`**（便于与 PC `dist` 分离发布）。  
- 「自动转」= 检测到手机访问 **主站入口**（`/`、`/login`、`/dashboard` 等）时，**重定向或引导到** `/h5/` 对应页。  
- 用户书签、短信里仍可只写主站域名；**不需要**特意输入 `.../h5/`。

**推荐实现方式（研发时二选一或组合，方案层先定体验）**

| 方式 | 做法 | 优点 | 注意 |
|------|------|------|------|
| **A. PC 入口探测（推荐一期）** | PC 的 `Login` / 根路由首屏用 UA 或窄屏判断 → `location.replace('/h5/...')` | 改动小、易回滚；不依赖 Nginx 改 UA | 需排除分享路径；可加 `?pc=1` 强制留 PC |
| **B. Nginx UA 分流** | 对 `/`、`/login` 等按 `User-Agent` 直接 rewrite 到 `/h5/` | 未下载大包 PC 资源前就分流 | 规则要维护；平板/桌面模式手机需例外 |

一期建议：**方式 A 为主**（快速落地）；稳定后再视需要加 B。

**建议规则**

1. **触发自动转 H5**：访问主站业务入口且判定为手机（UA，可辅以屏宽）。  
2. **不自动转**：`/share/*`、`/performance/share/*`、`/publish/*`、`/api/*`、静态资源。  
3. **逃生口**：`?pc=1` 或「在电脑版打开」→ 不跳转 / 从 H5 回到 PC（运维救急、特殊机型）。  
4. **H5 → PC**：H5「我的」可放「电脑版」说明（同域打开 PC 登录），非必须一期。  
5. **已登录态**：跳转时尽量带上 Token 或走同一 `localStorage` 同源策略，避免手机跳过去还要再登一次（实现细节在接口清单里定）。

```
手机打开 https://news.xxx.com/login（或 /）
        │
        ▼
  判定为移动端？ ──否──►  PC 登录 / Dashboard
        │是
        ▼
  重定向到 /h5/login 或 /h5/（已登录则进首页）
        │
        ▼
  H5 只读排版（舆情等）
```

**和「必须输入 /h5/ 链接」的区别**：后者否决。`/h5/` 只是技术挂载点；**产品入口 = 现有官网同址**。

## 2. 现网产品盘点：哪些适合 H5「只读」

按 Dashboard 现有应用逐项评估（**手机查看价值 × 现有只读 API/结构友好度 × 改造成本**）。

图例：

- **适合**：信息流/卡片易落地，接口清晰，移动场景真实  
- **可做但靠后**：能只读，但宽表/多维/图表重，成本高或手机价值一般  
- **不适合 / 排除**：本质是配置、作业台、写操作，或与「只看结果」不符  

### 2.1 新闻舆情

| 页面 | PC 形态 | H5 只读可行性 | 建议 |
|------|---------|---------------|------|
| **舆情信息** | 用户：`/api/news/user-news` + 时间 Tab；管理员：全量列表；另有导出/发布/AI 重跑等 | **高**。列表→详情（标题、企业、情绪、摘要、原文链）天然适合手机；用户侧接口已按「我的企业」隔离 | **一期首选 MVP** |
| 舆情监控对象 | 宽表 CRUD、导入、同步 | **低～中**。只读名单手机价值弱，且偏「配置对象」而非「结果」 | **不上或很后**；维护永远 PC |
| 数据库连接配置 | 配置 | 排除 | 不上 |

补充：**已确认** — 管理员用 H5 时与普通用户相同，只走「我的企业相关」；PC 上的全量舆情 / 收件人 / 发布仍仅 PC。

### 2.2 上市进展

| 页面 | PC 形态 | H5 只读可行性 | 建议 |
|------|---------|---------------|------|
| **打新日历** | 列表 + 同步/AI 命名/导出 | **中高**。日期、市场、标的名等「查一下」场景强；去掉同步/AI/导出后可做卡片或按日分组列表 | **二期优先候选** |
| 底层项目上市进展 | 多列表头进展表、分享等 | **中**。适合「跟项目状态」，但列多，需收敛字段做详情卡 | **二期～三期** |
| 上市信息表 / 底层项目表 | 主数据宽表 | **低**。偏台账，手机扫表体验差 | 暂缓或仅关键词搜+极简详情 |
| 数据库连接配置 | 配置 | 排除 | 不上 |

### 2.3 项目挖掘

| 页面 | PC 形态 | H5 只读可行性 | 建议 |
|------|---------|---------------|------|
| 融资与市场概览 | 概览/图表 | **中**。只读图表可做，需单独移动布局 | 三期再议 |
| **融资事件列表** | 事件表 + 同步/AI  enrichment/百科/导入导出 | **中**。事件流适合手机，但 PC 页写操作极多，H5 必须严格裁成「列表+详情只读」 | **二期～三期**（排在打新之后更稳） |
| 赛道配置 / DB 配置 | 配置 | 排除 | 不上 |

### 2.4 竞品分析

| 页面 | PC 形态 | H5 只读可行性 | 建议 |
|------|---------|---------------|------|
| 投前/投后竞品分析、底层项目 | 作业台：匹配、确认、补充、AI、复核抽屉等 | **低**。交互重，不是「看结果」而是「做分析」 | **长期不进 H5**（除非未来单独做「只读结论页」另立项） |
| 各类配置 / DB | 配置 | 排除 | 不上 |

### 2.5 项目估值

| 页面 | PC 形态 | H5 只读可行性 | 建议 |
|------|---------|---------------|------|
| 项目估值 Hub / 工作台 | 案例列表 + 多面板推演、导入财务、敏感性等 | **低～中**。工作台不适配；若仅「案例列表 + 已保存结果摘要」可只读，但字段与版本复杂 | **三期以后**；工作台永不进 H5 |
| DB 配置 | 配置 | 排除 | 不上 |

### 2.6 业绩看板

| 页面 | PC 形态 | H5 只读可行性 | 建议 |
|------|---------|---------------|------|
| 业绩看板 | 多版本、多指标、多层下钻、大量导出 | **中**。图表可移动化，但信息架构深、接口面大 | **三期+** 单独「精简只读看板」立项，勿塞进一期 |
| 业绩看板设置 | 配置 | 排除 | 不上 |

### 2.7 管理员设置与其它

用户管理、系统配置、企业列表、邮件收发、定时任务、私有公众号专队、we-mp-rss、额外公众号管理等 → **全部 PC-only**。

分享/发布页 → **不进 H5 产品**（见 §0）。

### 2.8 适合度总表（决策用）

| 优先级建议 | 模块 | 理由（一句话） |
|------------|------|----------------|
| P0 一期 | 账号密码登录 + 壳 + **舆情信息只读** | 最高频「看结果」；`user-news` 现成；卡片化成本最低 |
| P1 二期 | **打新日历只读** | 强移动场景；裁掉同步/AI/导出即可 |
| P2 二期后段或三期 | **底层项目上市进展只读**（字段收敛） | 跟进展有价值，改造量大于舆情/打新 |
| P2～P3 | 融资事件只读 | 事件流合适，但要与 PC 重操作页严格切开 |
| P3+ | 业绩看板精简只读 / 估值结果摘要 | 价值有，但工程与产品设计量大，单独立项 |
| 不上 | 竞品作业台、估值工作台、一切配置、分享页、专队 | 与「只读看结果」冲突或 ROI 差 |

## 3. 工程与身份（相对 v0.2 的调整）

### 3.1 仍锁定路线 C + 同址跳转

- 工程：`news/client-h5`（Vite + React 18 + 移动端组件库）  
- 部署：同域，H5 静态挂 `/h5/`；API 走同域 `/api`  
- 与 PC `client` 隔离构建  
- **PC 入口增加移动探测跳转**（见 §1.1），保证「同一地址 → 手机自动 H5」  

### 3.2 身份：一期密码登录，免登暂缓

```
（手机）同址 /login ──跳转──► /h5/login
                              → POST /api/auth/login → 存 Token
                              → 拉用户与 app_permissions
                              → 进入只读首页
```

- 与 PC **同一账号体系**；无权限则不展示对应入口。  
- **免登**（企微/钉钉）不进一期排期；后续可在同壳增加 `/h5/auth/callback`，不推翻路由结构。  
- 不做匿名进站；不做分享 Token 进 H5。

### 3.3 只读纪律

- 前端：无新建/保存/删除/同步/导出/AI 触发按钮。  
- 后端：优先复用 GET；若需瘦身则 `/api/h5/*` 只读；写接口不在 H5 白名单。

## 4. 建议排期（供你判断）

以下为 **推荐排法**（人周为粗估，按 1 名熟悉本仓的前端 + 少量后端计）。

### 阶段 0 · 地基（约 0.5～1 周）

| 交付 | 说明 |
|------|------|
| `client-h5` 脚手架 | Vite、路由 `base: '/h5/'`、axios、鉴权封装 |
| 登录页 | 账号密码，复用现网登录 API |
| 应用壳 | 底栏/首页卡片，按 `app_permissions` 显隐 |
| **同址跳转** | PC `Login`/根路由：手机 UA（可辅屏宽）→ `replace` 到 `/h5/...`；排除分享路径；支持 `?pc=1` |
| Nginx 草案 | `/h5/` 静态 + `try_files`（文档级，实施时写入部署流程） |

**验收**：手机用**与 PC 相同的网址**打开 → 自动进入 H5 登录/壳；电脑打开仍是 PC；`/share/...` 不误跳。

### 阶段 1 · 一期 MVP（约 1～2 周）— **已确认**

| 交付 | 说明 |
|------|------|
| 舆情列表 | 时间范围（昨日/本周/…）+ 关键词；卡片流；分页或上拉加载 |
| 舆情详情 | 摘要、情绪、类型、关联企业、原文外链（系统浏览器打开） |
| 可选 | 用户侧简单统计条（昨日企业数/条数），有则展示、无则不做 |

**明确不做（一期）**：导出、发布、AI 重跑、勾选批量、管理员收件人、监控对象、打新、一切配置、分享入口、免登。

**验收**：有新闻舆情权限的账号，在手机上完成「登录 → 刷列表 → 看详情 → 点原文」。

### 阶段 2 · 二期（一期验收后再开，约 1～2 周）

**建议顺序**：先 **打新日历只读**，再视反馈做 **上市进展只读（字段精简）**。

| 顺序 | 交付 | 裁剪规则 |
|------|------|----------|
| 2a | 打新日历只读 | 仅列表/按日分组 + 详情字段；无同步、无 AI 命名、无导出 |
| 2b | 底层项目上市进展只读 | 列表关键列 + 详情；无分享管理、无编辑 |

### 阶段 3 · 以后（单独立项，不默认进路线图承诺）

- 融资事件只读  
- 业绩看板精简只读  
- 估值「已保存结果」摘要  
- 企业 IM 免登  

仍默认不上：竞品作业台、估值工作台、全部配置与专队、分享页产品化。

### 4.1 信息架构（一期）

**对外（用户感知）**：始终用主站同址（如 `/`、`/login`），手机自动落到 H5。

**对内（路由，可对用户透明）**：

```
/login 或 /          →（手机）重定向 → /h5/login 或 /h5/
/h5/login
/h5/                 → 首页（仅「舆情信息」等已开放只读卡片）
/h5/news             → 舆情列表
/h5/news/:id         → 舆情详情
/h5/me               → 当前用户 / 退出
```

二期示例（确认后再加）：`/h5/listing/new-share`、`/h5/listing/progress`。

### 4.2 为何一期只押「舆情」而不塞打新

1. 接口与权限模型最成熟（`user-news` / 时间范围已与邮件、PC 用户视角对齐）。  
2. 交互模型最简单（信息流），最容易验证「只读 H5 + 同域 + 密码登录」整条链路。  
3. 打新/上市虽也适合看，但多一套列表字段设计与回归；塞进一期会拉长「能不能用」的反馈周期。  
4. 你可在一期上线后，用真实使用情况决定二期先打新还是先上市进展。

若你判断 **打新与舆情同等刚需**，可将 2a 上收为「一期扩展」，工期按 +0.5～1 周估，方案仍建议 **分两个可独立验收的里程碑**，避免一次做不完。
