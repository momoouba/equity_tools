# 数据应用隔离与业务匹配说明

本文说明 **`applications` 应用维度** 在「上市进展底层匹配」「新闻舆情被投企业」「被投企业列表/导出」中的落库与查询规则，便于部署与排障时对照代码。

---

## 1. 上市进展：`ipo_project` 与公开数据匹配

### 1.1 数据含义

- **`ipo_progress`**：交易所/辅导/境外备案等**公开抓取**的审核进展，不按应用维度拆分；**不依赖** `data_app_id` 做业务含义区分。
- **`ipo_project`**：用户侧「底层项目」，通过列 **`data_app_id`** 区分应用（如「上市进展」「项目挖掘」），值为 **`applications.id`**。

### 1.2 匹配逻辑（`server/utils/listing/listingMatchRunner.js`）

- 仅 **`ipo_project.data_app_id`** 等于 **`applications` 中 `app_name = 上市进展` 的 id** 的底层项目，参与：
  - 与 **`ipo_progress`** 的全称规范化匹配，写入 **`ipo_project_progress`**；
  - 与 **`ipo_new_share`** 的「昨日上市」全称精确匹配。
- 若无法解析「上市进展」应用 id：本次**不参与**底层项目匹配（项目集合等价为空），避免误用其它应用底层项目。
- **批处理开始时的清理**（在能解析到上市进展 id，且本次会跑进展或打新匹配时）：
  - 执行 `DELETE`：删除 **`ipo_project_progress`** 中关联到 **`ipo_project` 且 `data_app_id` 非上市进展 id** 的历史行（可选按 `restrictProjectUserId` 只删当前用户维度下的进度行），减轻历史脏数据导致的列表多余展示。
- **底层项目 SQL 全量同步**（`ipoProjectSqlSyncRunner.js`）：
  - **不再**删除 `ipo_project_progress`；替换 `ipo_project` 后按 **`fund` + `sub`（空与 NULL 等价）+ `company`** 重挂 `ipo_project_f_id` 并刷新项目快照字段；无法匹配的新项目置 `ipo_project_f_id = NULL`，历史匹配行保留。
- **「昨日上市」状态回填**（`backfillYesterdayListedStatus`）：仅对 **`ipo_project_progress` JOIN `ipo_project` 且 `p.data_app_id` 为上市进展 id** 的行更新；无应用 id 时跳过回填。

### 1.3 运维注意

- 确保 **`applications`** 中存在 **`app_name = 上市进展`** 的记录；`ipo_project.data_app_id` 在库初始化中会对空值回填为该 id（见 `server/db.js`）。

## 2. 新闻舆情：`invested_enterprises` 与公开抓取/匹配

### 2.1 落库原则

- 表 **`invested_enterprises`** 同时存在 **`data_app_name`**（文案/兼容）与 **`data_app_id`**（**`applications.id`，写入以 id 为准**）。
- 新增/导入等写入路径在 `server/routes/enterprises.js` 的 `insertEnterpriseRow` 等处会解析应用名并写入 **`data_app_id`**。

### 2.2 查询过滤（`server/utils/investedEnterpriseNewsAppSql.js`）

新闻舆情相关链路（公众号、统一社会信用代码、企业匹配、邮件任务、分享权限等）中，对 **`invested_enterprises`** 的「仅新闻舆情应用」条件统一为导出的 SQL 片段：

- **`IE_NEWS_APP_FILTER_SQL`**：无表别名。
- **`IE_NEWS_APP_FILTER_SQL_IE`**：表别名为 `ie` 时使用。

语义为：

1. **`data_app_id`** 等于子查询得到的 **`applications` 中「新闻舆情」id**；或  
2. **`data_app_id` 为空** 且 **`data_app_name` 回退为「新闻舆情」**（兼容迁移前旧行）。

主要引用文件包括（不限于）：`server/routes/news.js`、`server/utils/newsAnalysis.js`、`server/routes/newsAnalysis.js`、`server/routes/newsShare.js`、`server/utils/scheduledEmailTasks.js`。

### 2.3 运维注意

- 确保 **`applications`** 中存在 **`app_name = 新闻舆情`**；`invested_enterprises.data_app_id` 在库初始化中可按 `data_app_name` 回填（见 `server/db.js`）。
- 仅依赖 **`data_app_name`** 且 **`data_app_id` 长期为空** 的旧行，仍可通过第 2 条回退命中；**建议**以业务写入路径补齐 **`data_app_id`**，与列表 API 严格按 id 筛选保持一致（见下节）。

## 3. 被投企业列表与导出 API（仅按 `data_app_id`）

### 3.1 接口行为

- **`GET /api/enterprises`**（列表）、**`GET /api/enterprises/export`**（导出）  
  请求仍通过查询参数 **`data_app_name`** 指定应用（如「新闻舆情」「项目挖掘」），服务端先 **`getApplicationIdByAppName`** 解析为 **`applications.id`**。
- 列表/导出 SQL 条件为：**`invested_enterprises.data_app_id <=> ?`**（**不再**使用 `data_app_name = ?` 作为列表筛选条件）。
- 若 **`applications` 中查不到对应应用**：返回 **400**，提示未配置该应用。

### 3.2 数据要求

- **`data_app_id` 为 NULL** 的行**不会**出现在上述列表/导出结果中。  
  若历史数据仅有 `data_app_name` 而无 id，需依赖库迁移回填或重新保存/导入以写入 **`data_app_id`**。

### 3.3 其它接口（未改为仅 id）

- 批量导入去重 **`checkDuplicateData`**、企业同步任务内按统一社会信用代码匹配等，仍可能使用 **`data_app_name`** 参与条件；与列表 API 分离，后续如需统一可再迭代。
