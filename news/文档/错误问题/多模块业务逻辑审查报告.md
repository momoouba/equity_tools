## 一、业绩看板模块

### HIGH 严重度

**#1 版本删除缺少事务保护（多表软删除可部分失败）**
- 文件：`server/routes/performance/version.js`，约 472-486 行
- 描述：`DELETE /versions/:version` 端点对 17 张表依次执行 `SET F_DeleteMark = 1`，但未包裹在事务中。若中途某表 UPDATE 失败（锁超时、连接断开等），已完成的表保持删除状态，未执行的表保留活跃，造成数据不一致。
- 影响：17 张业务表出现部分删除、部分残留的不一致状态，需手动修复数据库。

**#2 定时任务"数据清理"物理删除无事务保护**
- 文件：`server/routes/performance/scheduled.js`，约 217-243 行
- 描述：数据清理任务对 17 张表依次执行 `DELETE FROM`（物理删除），未使用事务。若中途失败，部分表数据已删除、部分残留。同时缺少并发锁，两个定时任务可能同时执行同一清理操作。
- 影响：不可恢复的部分数据丢失，版本数据跨表不一致。

**#3 IRR 计算在同日交易场景下返回无意义值**
- 文件：`server/routes/performance/transactionIrr.js`，约 31-36 行
- 描述：`computeIRR` 中，当所有交易发生在同一天时，所有 `periods = 0`，NPV 退化为金额之和，导数恒为 0，求解器在二分法中震荡 100 次后返回无意义值。函数未对这一退化情况做保护。
- 影响：基金所有交易同日时产生虚假 IRR 值（非 null），误导投资业绩判断。

**#4 `connection.query` 解构格式与 wrapper 可能不匹配**
- 文件：`server/routes/performance/transactionIrr.js`，约 176, 184 行；`version.js`，约 239, 272, 344 行
- 描述：使用 `const [fundRows] = await connection.query(...)` 解构，假设返回 `[rows, fields]`（mysql2 原始连接格式）。但若 `db.getConnection()` 返回的连接对 `.query()` 做了封装（像 `db.query` 那样直接返回 rows），则 `[fundRows]` 实际解构的是第一行数据而非数组。
- 影响：IRR 计算静默跳过所有基金，或版本创建循环静默跳过所有业务表插入，导致空看板。

**#5 SQL 注入面：动态表名防护脆弱**
- 文件：`server/routes/performance/version.js`，约 288-336 行
- 描述：`target_table` 来自 `b_sql` 数据库表，通过反引号转义插入 SQL。虽然有 `b_version` 黑名单检查（288 行），但仅做大小写不敏感精确匹配。带尾随空格的 `b_version ` 或 schema 限定的 `other_db.b_version` 可绕过。
- 影响：错误的 `b_sql.target_table` 配置可能向非预期表（包括 b_version）写入数据。

**#6 版本创建并发竞态：新日期首个版本号可能重复**
- 文件：`server/routes/performance/version.js`，约 239-256 行
- 描述：使用 `SELECT ... FOR UPDATE` 锁定最大版本号行。但当某日期尚无任何版本行时，`FOR UPDATE` 在空结果集上不获取锁（取决于隔离级别和索引），两个并发请求可能都看到 0 行并都创建 `V01`。
- 影响：重复版本标识符（如 `20250630V01`），导致后续数据写入冲突。

### MEDIUM 严重度

**#7 `ensureRowIds` 本地 ID 递增存在并发碰撞风险**
- 文件：`server/routes/performance/version.js`，约 60-87 行
- 描述：批量插入时，首次调用 `generateId` 后通过递增末 5 位生成后续 ID。若另一进程在 generateId 和 INSERT 之间插入了更高 ID，会导致主键冲突。
- 影响：`Duplicate entry for key 'PRIMARY'` 错误导致整个版本创建回滚。

**#8 导出端点无超时/行数限制——大数据集内存溢出**
- 文件：`server/routes/performance/export.js`，约 180-709 行
- 描述：所有导出端点将全部匹配行加载到内存、构建 XLSX 后返回。大型基金（数千 LP/交易）可消耗数百 MB 内存，并发导出可能使 Node.js OOM。
- 影响：服务器 OOM 崩溃或极慢响应。

**#9 数据清理保留条件依赖 `getDate()` 受时区影响**
- 文件：`server/routes/performance/scheduled.js`，约 208-214 行
- 描述：清理逻辑保留每月 1 号和 4 号创建的版本。但 `new Date(creatorTime).getDate()` 使用服务器本地时区。UTC 服务器上，UTC+8 的 6 月 1 日凌晨 2 点会被解析为 5 月 31 日 18:00 UTC，`.getDate()` 返回 31 而非 1。
- 影响：应保留的月度快照版本可能被错误删除。

**#10 分享 `/data` 端点未实现——始终返回空数据**
- 文件：`server/routes/performance/share.js`，约 231-245 行
- 描述：`/share/data` 端点有 TODO 标记，始终返回 `manager: null, funds: [], portfolio: null, underlying: null`。
- 影响：分享功能不可用，外部用户看到的是空看板。

**#11 分享密码校验绕过：`has_password=1` 但 `password_hash=null` 时跳过检查**
- 文件：`server/routes/performance/share.js`，约 170-178, 224-229 行
- 描述：密码检查条件为 `if (link.has_password && link.password_hash)`。若创建分享链接时勾选"有密码"但密码为空字符串（58 行的 `if (hasPassword && password)` 跳过哈希生成），`password_hash` 为 null，密码检查被完全跳过。
- 影响：虚假安全感——用户以为设置了密码保护，实际任何有链接的人都能访问。

**#12 指标配置 PUT 端点 SELECT→INSERT 竞态**
- 文件：`server/routes/performance/config.js`，约 197-269 行
- 描述：先 SELECT 检查配置是否存在，再决定 INSERT 或 UPDATE。两个并发 PUT 请求可能都看到不存在并都执行 INSERT，导致重复配置行或唯一约束冲突。
- 影响：重复配置数据或 500 错误。

**#13 `replaceVersionInSql` 单引号转义不足以防 SQL 注入**
- 文件：`server/routes/performance/config.js`，约 554-561 行
- 描述：`replaceVersionInSql` 用 `.replace(/'/g, "''")`转义单引号。当前版本号由系统生成是安全的，但该函数作为模块导出，若被误用于用户输入，在 MySQL `NO_BACKSLASH_ESCAPES` 关闭时可能被反斜杠绕过。
- 影响：当前低风险，但存在未来误用隐患。

**#14 `getShanghaiNow()` 仅在 UTC 或 UTC+8 服务器正确**
- 文件：`server/routes/performance/version.js`，约 26-32 行；`scheduled.js`，约 14-20 行
- 描述：通过偏移量计算转为上海时间，但 `Date.getHours()` 始终以服务器本地时区解析内部 UTC 时间戳。仅在 UTC 或 UTC+8 服务器上结果正确，其他时区（如 UTC-5）返回错误时间。
- 影响：非 UTC/UTC+8 时区部署时，版本创建时间和"月末最后一天"判断错误。

**#15 定时任务自调用未转发 `X-User-Id` 头**
- 文件：`server/routes/performance/scheduled.js`，约 261-275 行
- 描述：定时任务执行器向本地 `/api/performance/versions` 发 POST 请求时转发了 cookie 和 authorization，但未转发 `X-User-Id`。创建的版本 `creatorId` 为 null，被当作系统生成版本。
- 影响：影响审计追踪，且与清理逻辑的 `!creatorId` 判断交互，可能导致意外删除。

### LOW 严重度

**#16** `dashboard.js` `/underlying` 端点对 `b_project_all` 执行两次几乎相同的查询（仅 SELECT 列不同），可合并为一次查询。

**#17** `config.js` INSERT 新指标配置时 `F_LastModifyUserId` 和 `F_LastModifyTime` 设为 null，与 `F_CreatorTime` 不一致。

**#18** `export.js` 所有数值统一 `toFixed(2)` 导致整数显示 `.00` 后缀，IRR 小数丢失精度。

**#19** 版本号解析用正则 `match(/V(\d+)$/)` 但列表排序用 `SUBSTRING_INDEX(version, 'V', -1)`，对畸形版本号行为不一致。

**#20** `scheduled.js` 物理删除时不检查 `F_DeleteMark`，可能误删同标识符的新版本数据。

## 二、上市进展模块

### HIGH 严重度

**#1 SQL 同步全量替换：外部查询返回空集时数据丢失**
- 文件：`server/utils/listing/ipoProjectSqlSyncRunner.js`，约 384-426 行
- 描述：同步逻辑先 DELETE 用户所有 `ipo_project` 行，再 INSERT 新行。当外部查询返回空集（如外部数据库故障返回空结果）时，`prepared.length === 0` 仍然执行了删除操作。守卫条件 `externalRows.length > 0 && prepared.length === 0` 不覆盖 `externalRows.length === 0` 的情况。
- 影响：外部数据库返回空集时，所有用户项目数据被清空，`ipo_project_progress` 记录全部变为孤儿（`ipo_project_f_id = NULL`）。

**#9 北交所爬虫循环中 `return` 误用为 `continue`**
- 文件：`server/utils/listing/listingExchangeCrawler.js`，约 808, 864 行
- 描述：在 `for (let i = 0; i < detailTargets.length; i += 1)` 循环中，当 id 为空（808 行）或 HTML 为空（864 行）时使用 `return` 而非 `continue`。`return` 会退出整个函数，导致后续所有 detailTargets 被跳过。
- 影响：北交所状态日期补全在遇到第一个无效 id 或空页面时提前终止，大量记录缺少正确的状态日期。

**#15 `assertReadOnlySql` 安全检查不够严格**
- 文件：`server/utils/listing/ipoProjectSqlSyncRunner.js`，约 20-28 行
- 描述：仅检查首个关键词是否为 `select` 或 `with`。但 MySQL 的 `SELECT ... INTO OUTFILE` 可写文件，`SELECT ... INTO @var` 可设置变量，多语句 SQL（如 `SELECT 1; DROP TABLE ipo_project`）在驱动支持多语句时可造成破坏。
- 影响：恶意或错误配置的 SQL 可通过"预览"和"执行"接口造成数据泄漏或破坏。

### MEDIUM 严重度

**#2** IPO SQL 同步 `listing` 目标使用过宽的 `data_app_id` 匹配，`data_app_id IS NULL` 条件会删除其他应用的遗留数据。

## 三、竞品分析模块

### HIGH 严重度

**#1 `validateCandidate` 在 AI 空响应或解析失败时默认通过验证**
- 文件：`server/utils/competitor-analysis/competitorAnalysisAi.js`，约 278-308 行
- 描述：AI 返回空/null 内容时，`extractJsonObject(raw)` 返回 null，条件判断失败后走到默认返回：`is_competitor: true, validated_score: 50`。AI 异常（超时、限流等）被 catch 后同样返回此默认值。
- 影响：AI 调用失败的候选公司被视为通过的竞品（50 分），假阳性竞品进入最终结果。

**#2 LLM 调用无 prompt 内容长度截断**
- 文件：`server/utils/competitor-analysis/competitorAnalysisAi.js`，约 14-37 行（prompt 构建），112-186 行（`invokeCompetitorChat`）
- 描述：prompt 构建函数直接 `JSON.stringify` 目标/候选对象，无长度上限。`pair_similarity` 的 user message 可超过 10,000 字符，`web_discover` 含 30 个排除公司名的 prompt 更长。`newsAnalysis.js` 有 5000 字符截断保护。
- 影响：超出模型上下文限制导致 400/413 错误，浪费配额和时间，可能降低模型质量。

**#3 `discoverWebCompetitors` 将 AI 空响应视为"零候选"而非失败**
- 文件：`server/utils/competitor-analysis/competitorAnalysisAi.js`，约 219-276 行
- 描述：`invokeCompetitorChat` 返回 undefined 时，`extractJsonObject` 返回 null，代码返回 `{ candidates: [] }`——与 AI 成功运行但未发现竞品的结果相同。HTTP 200 空内容不触发重试。
- 影响：瞬态 AI 问题被静默当作"无竞品发现"，永久降低该次运行的召回率，且无日志区分。

**#4 `scorePairSimilarity` 在 AI 空响应时静默退化为文本重叠分数**
- 文件：`server/utils/competitor-analysis/competitorAnalysisAi.js`，约 188-212 行
- 描述：AI 返回空时，`parsed.similarity_score` 为 undefined，`Number(undefined)` 为 NaN，代码退化到 `textOverlapFallback`（基于 bigram 的文本相似度）。该 catch 块捕获所有异常，即使重试耗尽后的真正错误也静默降级。
- 影响：LLM 产品相似度评分变为文本重叠评分，无任何降级标记。对于简短或通用介绍文本的公司，产生人为偏低/偏高的分数，影响最终竞品排名。

**#5 投资企业/IPO 项目 AI 补全将空结果标记为成功（与投前项目不一致）**
- 文件：`server/utils/competitor-analysis/investedEnterpriseAiEnrichService.js`，约 236-284 行；`ipoProjectAiEnrichService.js`，约 237-297 行
- 描述：三个 AI 补全服务对空 LLM 结果处理不一致：
  - **preInvestmentProjectAiEnrichService**（正确）：检查空结果后抛出 Error，状态标记为 `failed`
  - **investedEnterpriseAiEnrichService**（有 bug）：仅 `console.warn`，将空数据写入数据库，状态标记为 `success`
  - **ipoProjectAiEnrichService**（有 bug）：无空结果检查，静默写入空数据并标记为 `success`，还传播给同信用代码的其他 IPO 项目
- 影响：空 AI 结果的企业/IPO 项目被错误标记为成功补全，后续竞品分析使用空字段匹配降低召回率，`only_failed` 批量重试不会重新处理这些记录。

### MEDIUM 严重度

**#6** `run_id` 查询竞品关系时遗漏 `delete_mark = 0` 过滤，历史运行的软删除关系仍可见。

**#7** `buildFinancingEventIndex` 将整个融资事件表加载到内存（可能数万条记录），并发分析运行时每份创建完整副本。

**#8** `candidateDedupeKey` 在信用代码和名称都为空时退化为 `Math.random()`，去重失效。

**#9** 持久化阶段的 LLM 补全调用（每个关系一次）显著增加延迟，10-30 个竞品 × 5-30 秒/次 = 2-10 分钟。

**#10** 导出工作簿忽略 `years` 过滤器对竞品关系的筛选——选定年份后导出的是该企业所有历史竞品关系。

**#11** 非管理员导出 `exportAll` 模式跳过所有权验证，可导出所有企业的竞品数据。

**#12** `competitorAnalysisRunner.js` 自动扩展逻辑在结果过少时放宽过滤条件，可能重新包含已被 AI 验证拒绝的非竞品/上下游公司。

**#13** `mergeTagArrays` 在两个模块中有不同实现——工具版本上限 32 标签，就绪度服务版本上限 24 标签。

### LOW 严重度

**#14** `clientIpFromReq` 函数在 3 个路由文件中重复。

**#15** `listInvestedEnterpriseYears` 对非管理员用户执行两次查询（先全量后限定），第一次结果被丢弃。

**#16** `dedupeRelations` 使用 `String(r.created_at)` 字符串比较排序，数据库驱动返回非 ISO 格式时排序错误。

**#17** `collectCompetitorLookupKeys` 添加冗余的小写信用代码键（规范键始终为大写）。

## 四、项目挖掘模块

### HIGH 严重度

**#1 "千万"融资金额解析为实际值的 1/1000**
- 文件：`server/utils/project-sourcing/financingAmountParse.js`，约 50-80 行
- 描述：`parseFinancingMoneyText()` 处理"万"（10⁴）和"亿"（10⁸），但未处理"千万"（10⁷）。对于"3千万"：`numMatch` 捕获 `3`，`hasWan = true`（因为"千万"包含"万"），结果 = `3 × 10⁴ = 30000`。正确值应为 30,000,000。**偏差 1000 倍。**
- 影响：含"千万"的融资金额存储为实际值的千分之一，严重影响投资分析和筛选。

**#2 DashScope 降级仅处理 HTTP 400，不处理 429/5xx**
- 文件：`server/utils/project-sourcing/financingAiEnrichDashScopeChat.js`，约 189-270 行
- 描述：降级链（搜索+思考 → 仅搜索 → 无搜索 → 无搜索无思考）仅在 HTTP 400 时触发。HTTP 429（限流）、500（服务端错误）、502/503 或网络超时直接传播错误。代码 198-199 行：`if (!isHttp400(err)) { throw err; }`。
- 影响：限流错误被当作致命错误，而应触发退避重试。

**#3 行业标准化种子映射仅 3 条——基本不可用**
- 文件：`server/utils/project-sourcing/financingIndustryMap.js`，约 7-11 行
- 描述：`SEED_MAP` 仅包含 3 个映射："文娱传媒/媒体"、"人工智能/人工智能基础技术"、"人工智能/(任意 lv2)"。其他所有行业分类结果为 null。
- 影响：标准行业分类对绝大多数记录无效，行业分析功能基本不可用。

**#4 AI 补全任务无瞬时错误重试机制**
- 文件：`server/utils/project-sourcing/financingAiEnrichService.js`，约 1823-1962 行
- 描述：`callDashScopeOpenAIChat` 因瞬时错误（网络超时、500、429）失败时，任务被永久标记为 `failed`，无自动重试。对比 `syncFinancingDateRange` 实现了 5 次指数退避重试。
- 影响：DashScope 瞬态中断导致融资事件被永久标记为 `ai_enrich_status=failed`。

**#5 `invokeProjectMiningChat` 不验证 AI 响应**
- 文件：`server/utils/project-sourcing/projectMiningAi.js`，约 34 行
- 描述：直接委托给 `callAIModel()` 无任何验证。若返回 null、undefined 或空字符串，调用方需自行处理。
- 影响：空 AI 响应可能导致下游逻辑异常。

## 跨模块共性问题

以下问题在多个模块中重复出现，建议作为统一改进方向：

### 1. AI 空响应处理不一致
`newsAnalysis.js` 已修复了显式空响应检查和日志。但竞品分析（5 个 HIGH）、项目挖掘（2 个 HIGH）、上市进展均缺少类似的统一防护。建议抽取公共 `validateAiResponse()` 工具函数。

### 2. 多步写操作缺少事务保护
业绩看板（版本删除、数据清理）、上市进展（批量导入）、项目挖掘（Excel 导入）均存在非事务性多步写入问题。建议所有涉及多表写入的操作统一使用 `connection.beginTransaction()` / `commit()` / `rollback()`。

### 3. 定时任务缺少幂等性和并发保护
上市进展（`runningTaskKeys` 内存锁重启丢失）、项目挖掘（无并发锁）、业绩看板（清理任务无锁）均存在定时任务并发执行风险。建议引入数据库级别的分布式锁或 Redis 锁。

### 4. 失败日期/批次永久跳过
上市进展（`last_sync_range_end` 部分交易所失败仍推进）、项目挖掘（`last_sync_time` 全部失败仍更新）均存在失败数据被永久跳过的问题。建议仅在所有子任务成功后才推进同步位点。

### 5. Prompt 长度无限制
`newsAnalysis.js` 已有 5000 字符截断保护。竞品分析的所有 LLM 调用均无 prompt 长度限制，可能导致超出上下文窗口、浪费 token 配额。

---

> 本报告共计 HIGH 19 项、MEDIUM 37 项、LOW 31+ 项。建议优先处理各模块的 HIGH 项和跨模块共性问题。
