一、文档概述

本文档明确上市进展管理系统的核心需求、数据表设计、业务逻辑、前端页面及验收标准，用于开发落地、测试评审、上线验收，全程遵循系统现有组件复用原则，确保功能闭环、可执行性强。

核心范围：三大交易所 IPO 进展爬取与存储、底层项目管理、业务数据库 SQL 同步、项目与进展匹配、权限与菜单、**系统配置中的上市数据配置（含 Cron）**、邮件与收件管理、日志与重试策略对齐新闻模块；**【一级市场扩展 · 新增 · 2026-04-13】** **一级市场扩展**：新股申购日历（打新提醒，含上市首日指标补齐）、各地证监局上市辅导备案信息抓取与入库；**【打新日历数据源与抓取规则 · 新增 · 2026-04-14】** 明确打新日历各所公开页 URL、`ipo_new_share` 创建/更新时间、按股票代码去重、字段补全后再停抓、北交所不写中签率；**【港股经济通数据源 · 新增 · 2026-04-15】** 港股打新日历默认走 **经济通**（`stocks.etnetchina.cn` 同源香港站页面，见 **14.1.2**、**14.2.2**），可按环境变量回退港交所静态表或 AkShare 港股行情；**【港股申购上限口径 · 修订 · 2026-04-16】** 港股 **`limit_shares`** 按经济通 **`maxlotsize`×`boardlot`（股）** 入库（见 **14.1.2**）；**【证监会辅导备案抓取 · 新增 · 2026-04-15】** 证监会 **辅导企业** 公开列表抓取、备案时间倒序、定时按前一日/手动按时间区间筛选、空列表重试、仅抓取备案时间与辅导对象并直接写入 **`ipo_progress`**；**【境内企业境外上市备案审核抓取 · 新增 · 2026-04-15】** 从证监会政府信息公开页定位审核进展公告并下载 Excel，提取备案审核字段，**按 15.8 写入 `ipo_progress`** 并参与上市进展匹配；**【证监会政府信息公开·备案通知书列表抓取 · 新增 · 2026-04-20】** 证监会「境外证券发行」**列表页**备案通知书走 **详情 HTML** 入库 **`ipo_progress`**，与 Excel 行 **同企业同日合并**（见 **14.5、15.8.1、16.3**）；**工程代码按「业绩看板应用」模式独立目录存放，文件夹统一命名为「上市进展」**（见第十六节）。

二、权限、管理员与菜单

1. **第三条顶层分组「上市进展」**：权限位类似 **`hasListingPermission`**（命名以实现为准）。
2. **管理员判定（写死）**：系统用户 **`users.account === 'admin'`** 的账号为管理员，享有文档中全部「仅 admin」能力。
3. **普通用户**：须经授权具备「上市进展」菜单权限后方可访问对应接口与页面；**无上市进展权限的用户不得创建上市进展相关的收件规则**（见「收件与邮件」）。
4. **数据访问**：核心业务表**不设计业务 `app_id` 字段**；行级数据结合**菜单权限**与 **创建人 / 管理员** 规则鉴权（见「接口约定」）。

五、接口约定

1. **`GET /ipo_project`（及同类列表查询）**：**默认永远带 `creator_id = currentUser`**；**仅当请求者为 admin（`users.account === 'admin'`）时可不带该条件或查询他人数据**（与「底层项目表」管理员按用户筛选一致）。
2. 其他资源的创建人规则仍以文档及现有中间件为准。
3. **发送邮件与同步行为区分（强制）**：`发送邮件` 仅发送当前已入库数据，**不触发抓取任务**；前端按钮旁与二次确认弹窗必须展示提示文案：`仅发送已入库数据，不触发抓取`。
4. **判重前统一标准化（强制）**：所有入库判重键在比较前必须执行统一标准化函数（至少包含：前后空格清洗、连续空白压缩、全角/半角括号统一、公司名括号去除但保留括号内文本）；未经标准化不得直接参与去重判断。
5. **空值展示与导出口径（强制）**：前端表格字段空值统一显示 `-`；导出文件保留原始空值（空单元格），不得写入 `-`。

六、收件与邮件

1. **收件配置表**：使用 **`recipient_management`** 存储收件人等内容；该表 **新增字段 `app_id`**（VARCHAR，对应 `applications.id`）：
   - **新闻舆情** 场景：存 **新闻舆情** 对应应用的 `app_id`；
   - **上市进展** 场景：存 **上市进展** 对应应用的 `app_id`。
2. **`applications` 表初始化（或迁移）一条应用记录（写死逻辑）**：
   - **id**：`2026033000000000001`
   - **名称**：`上市进展`
   - **创建时间**：`2026-03-30 18:00:00`（若表结构仅有名称等字段，以实现为准，**id 与名称不得冲突**）。
3. **`email_config`**：**必须存在「上市进展」应用** 对应的邮件配置记录，**用于上市进展发信**；**与新闻舆情应用配置分离**，**逻辑写死**：发上市进展类邮件时 **只解析并使用 `app_id = 上市进展应用 id` 的 `email_config`**。

八、定时爬取、节假日与匹配批次

1. **每日自动爬取** 由 **系统配置 → 上市数据配置** 中的 **Cron 表达式** 定义 **北京时间** 触发时刻；到点自动执行 **爬虫或数据接口** 配置。
2. **抓取时间窗**：默认定时任务 **抓取「前一日」** 上市进展（与第七节 SQL 中「前一日」为 **同一套语义**）。
3. **节假日**：若定时任务配置为 **跳过节假日**，则本次执行应 **补抓「节假日前一自然日」至「当前执行日的前一自然日」** 区间内尚未入库的数据（具体边界以实现与 Cron 库行为为准，需写测试用例）。
4. **同日多次触发**：对已抓取内容 **追加尚未写入数据库的数据**（幂等：不重复插入已存在主键或业务唯一键，以实现为准）。
5. **匹配时 SQL 语义示例**（与「前一日」一致）：匹配操作可选用类似  
   `WHERE DATE(ip.f_update_time) = DATE_SUB(CURDATE(), INTERVAL 1 DAY)`  
   表示 **进展侧更新日期为北京时间「昨日」** 的批次参与匹配（与手动发信 **无范围** 不冲突）。
6. **时区强约束（新增）**：所有 Cron 触发、窗口计算、`前一日/上周` 判定统一使用 **`Asia/Shanghai`**，不得依赖服务器本地时区。
7. **并发互斥（新增）**：同一 `数据源类型 + 时间窗口` 若已有任务运行中，后续触发（含定时与手动）默认 **拒绝执行并记录日志**（可配置为排队模式时需全局统一，不得混用）。

- 首日指标补抓必须复用打新日历任务，不新增独立调度任务。

1. **第一步：抓前一日上市清单（T 日）**  
   每日定时任务先调用 `stock_xgsr_ths`，筛选 **上市日期 = 前一自然日** 的新股，写入/更新候选清单。

**手动触发**

- 手动同步时按时间区间筛选候选股票，并执行同样的首日指标补抓与空值更新。

**停抓示例**

- 例如某股 **2026/4/13** 上市（T 日），首日指标按 T 日或首个成交日抓取；后续同步若该日指标曾为空则继续补抓直至补齐。

#### 14.3.1 【证监会辅导备案抓取 · 新增 · 2026-04-15】

**列表入口（证监会）**

- **URL**：http://eid.csrc.gov.cn/csrcfd/index.html

**列表交互（必选）**

- 抓取前须 **模拟用户点击列表表头「备案时间」列**，使列表按 **备案时间倒序**（新在前）排列，保证分页与「按日截取」时序正确、与定时筛选语义一致。
- 列表解析时须同时抓取页面列 **派出机构**，并映射写入 `ipo_progress.register_address`；若页面无该列或为空，允许写空，前端统一展示为 `-`。

**定时任务 — 按「前一日」备案时间筛选**

- **时间口径**：与第八节「前一日」一致，**中国北京时间**自然日。
- **筛选字段（统一）**：以页面 **「备案时间」** 解析并映射至 `ipo_progress.f_update_time`；定时任务每次执行时，仅处理 `DATE(f_update_time) = 执行日-1` 的记录（`Asia/Shanghai`，闭区间单日）。

**手动触发 — 按时间区间筛选**

- 手动同步时，若用户选择时间区间 **`[from, to]`**，则仅抓取并处理 `DATE(f_update_time)` 落在该闭区间内的数据。

**手动触发 — 空列表重试**

- 手动同步/查询时，页面或接口可能返回 **空列表**（加载未完成、会话抖动、反爬等）。
- **要求**：若本次查询结果为空，须 **自动重新发起查询/拉取**（重新打开列表或重复请求），**直至** 成功拿到非空列表并完成解析，或达到实现侧配置的 **最大重试次数 / 总超时**（须打日志，避免无限循环）。

**入库规则 — 仅按备案时间 + 辅导对象**

- **本需求抓取字段**仅包含：辅导对象（映射 `ipo_progress.company`）与备案时间（映射 `ipo_progress.f_update_time`）。  
- 由于列表中的**辅导状态变化不提供可靠更新时间**，本期**不抓取也不基于状态变更入库**；状态变化类信息按本需求逻辑无法稳定识别。  
- **去重建议键**：`company(标准化后)` + `exchange='证监会辅导备案'` + `DATE(f_update_time)`（若实现需区分分局，可叠加 `register_address`）。  
- 若待写入行命中去重键已存在记录 → **SKIP**；未命中 → **INSERT**。
- **直接入 `ipo_progress`（强制）**：证监会辅导备案数据不落独立 `ipo_guidance` 表，解析后直接按上表映射写入 `ipo_progress`，用于统一在上市进展主列表与匹配流程中展示。

**示例（按本期简化逻辑）**

- **定时任务抓昨天**：系统日为 2026-04-19，则仅处理 `DATE(f_update_time)=2026-04-18` 的辅导对象行。  
- **手动抓区间**：选择 `2026-04-01 ~ 2026-04-30`，则仅处理该区间内 `DATE(f_update_time)` 命中的行。  
- **状态变化场景**：即使同一辅导对象后续状态文案发生变化，只要本期抓取字段仍是“备案时间+辅导对象”，系统也**不做状态变化入库判断**。

**反爬与编码**：与第十二节日志要求一致；失败可告警；字段映射以 **15.7** 为准。

**项目编号（`project_no`）生成规则**

- **格式**：`PP` + **年月日（YYYYMMDD，8 位）** + **5 位序号**（自 `00001` 起左侧补零），示例：`PP2026033000001`。
- **生成逻辑**：与 `invested_enterprises` 表中 **`project_number`** 的实现一致（参见 `server/routes/enterprises.js` 中 `generateProjectNumber`）：以 **`PP` + 当前日期的 `YYYYMMDD`** 为前缀，在 **`ipo_project` 表** 中查询当日已存在的最大 `project_no`，序号 **+1**；若无则序号为 `1`；最终拼接为 **前缀 + 5 位序号**。
- **与舆情被投的差异**：舆情被投为前缀 **`P`**，上市进展底层项目为前缀 **`PP`**，其余（按日滚动序号、5 位宽度、同日递增）**同一套算法**。

**去重（业务库 SQL 定时更新）**：**归属基金 + 归属子基金 + 企业全称**；命中后若 **剩余金额、穿透权益占比、穿透剩余金额** 与库内不一致则 **更新** 业务列，**项目编号不变**，并刷新 **biz_update_time**。

**批量导入去重**：若与 SQL 同步键不同，以实现与模板约定为准（可单独配置为 **基金 + 子基金 + 项目简称** 等，需与产品一致）。
