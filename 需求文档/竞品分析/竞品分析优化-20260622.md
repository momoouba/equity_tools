# 竞品分析优化方案

> 编制日期：2026-06-22（2026-06-23 评审修订）
> 基于现有系统分析 + 《竞品分析Agent模型与维度建议.pdf》+ 用户反馈 + 方案评审综合整理

---

## 方案定位（评审结论）

本方案定位为 **Phase 1 产品优化**：在现有 S0–S6 架构内，通过 S5 结构化输出升级、规则微调与前端分层展示，快速提升投研可用性。

与 PDF 推荐的 **竞品 Agent 终态架构**（embedding 语义召回 → reranker 精排 → 证据抽取 → LLM 结构化判断 → 反馈闭环）相比，本文档**主要改「判断层表达」**，尚未触及 PDF 认定的最大短板——**语义召回质量、可追溯证据链、人工确认反馈闭环**。因此：

| 维度 | 评价 |
|------|------|
| 问题诊断 | 准确，与代码实现及 PDF 一致 |
| 短期可落地性 | 高，P0 项均无外部依赖，可立即交付 |
| 是否最优架构 | **否**——偏 Prompt/规则驱动升级；embedding + reranker 仍属下一阶段 |
| 最大风险 | 缺乏黄金评测集量化验证；语义召回质量未改善 |

**修订要点**：

1. **S3 保持轻量**：维持 similarity_score + rationale 输出，取消原方案的七维度 Prompt——维度评估统一由 S5 承担，避免两阶段重复判断和 token 成本翻倍。
2. **evidence_confidence 改为系统计算**：不再由 LLM 自评，而是系统根据 `evidence_sources` 来源级别 + 多源一致性自动计算，约束幻觉。
3. **负面排除改为标签级**：用 industry_l1/l2 或特定 tag 做精准排除，替代脆弱的文本关键词匹配。
4. **same_track 落库策略明确**：默认落库但 `include_in_comparable = 0`，前端默认隐藏，用户可切换查看。
5. **阈值参数化**：投前/投后使用不同落库阈值，1-2 行改动避免技术债。
6. **黄金评测集不阻塞开发**：先用 5-10 个 smoke test 并行启动，不作为前置阻塞项。

**并行建议**：执行本文 P0 的同时，**启动 embedding 离线 POC 与黄金评测集 smoke test**，避免陷入「Prompt 越写越长、漏召仍在、阈值无法证明」的局部最优。

## 一、现状问题总结

当前竞品分析管线（S0-S6）的核心能力是 **语义相似度匹配**，通过标签 Jaccard（35%）+ 产品介绍 bigram 重叠（40%）+ 行业分类（25%）做规则粗排，再经 LLM 对标打分和校验。

主要不足：

1. **规则打分的三个维度都偏向"像不像"而非"是否竞争"**：标签和文本相似度高不代表争夺同一客户、同一预算。
2. **标签权重隐性放大**：缺少 `industry_l1` 时，行业分退化为标签 Jaccard × 80，标签同时贡献 tagScore 和 industryScore，导致纯标签匹配的企业排名偏高。
3. **产品介绍用 bigram 字面重叠**：同一赛道公司常用不同话术描述同一能力，字面匹配容易漏判。
4. **LLM 判断维度单一且两阶段职责重叠**：S3 对标仅输出 similarity_score + rationale，S5 校验仅判断 is_competitor 和 is_upstream_downstream，缺乏竞品类型分类和结构化维度评估；若 S3 和 S5 均输出竞品类型则结论可能矛盾。
5. **无竞品类型区分**：直接竞品、间接竞品、替代品、上下游、仅同赛道一律混排。
6. **无负面排除机制**：用户无法在触发分析时指定"不要召回某类企业"。
7. **分数融合权重固定**：不根据数据质量（如简介长度、信息完整度）动态调整。
8. **阈值未区分投前/投后场景**：投前查重需高召回，投后监控需低噪音，当前统一阈值无法兼顾。
9. **证据不可核验**：LLM 结论缺乏可追溯的证据来源标记，投资经理无法区分"有据可查"与"模型推断"。

## 二、优化项清单

### 优化项 1：强化 S2 规则打分维度

**目标**：在现有三维度基础上修复标签双重计分问题（P0），规模/年限维度作为可选软惩罚按赛道开关（P2）。

**具体改动**：

**1.1 修复标签双重计分（P0，优先实施）**

现状：候选缺少 `industry_l1` 时，`industryScore = tagJaccard × 80`，与 `tagScore`（权重 0.35）叠加，标签被重复放大。仅调权重无法消除此问题。

建议：`industry_l1` 缺失时行业维**不参与计分**（权重按比例分给其余维度），或改用独立弱信号（如国标缺失时不回退标签 Jaccard）。

**涉及代码**：`competitorAnalysisRunner.js` — `ruleScoreCandidate()` 函数中 `else` 分支（当前为 `industryScore = Math.round(jaccardSimilarity(target.tags, cand.tags) * 80)`）。

**1.2 规模/年限软惩罚（P2，按赛道开关，须黄金集验证）**

从 `ipo_project` / `sourcing_financing_event` 已有字段中提取注册资本或最近一轮融资金额，计算目标与候选的规模比值：

```
scaleRatio = min(target, candidate) / max(target, candidate)
scaleScore = scaleRatio * 100
```

成立年限接近度：

```
yearDiff = |target成立年 - candidate成立年|
ageScore = max(0, 100 - yearDiff * 10)
```

**赛道限制**：规模/年限维度**必须按行业赛道开关**，不作为通用维度。在医药/生物科技赛道（`industry_l1` 匹配医药相关分类）**默认关闭**——因为该赛道频繁出现"初创 Biotech vs 大药企竞逐同一靶点"的情况，规模和年限差异不构成竞争关系的有效判据。在消费、SaaS 等赛道可考虑开启，但仍须在黄金集上验证 recall 不下降。

**数据来源**：`ipo_project` 表的注册资本字段、`sourcing_financing_event` 表的融资金额字段、企查查 brief 中的成立日期。若两端均无数据则跳过该维度、权重重新分配。

**1.3 调整现有三维度权重（P1，配合 1.1 修复后实施）**

修复 1.1 后，标签双重计分问题消除，可适度调整权重：

| 维度 | 原权重 | 新权重 | 说明 |
|------|--------|--------|------|
| 标签相似度 | 35% | 30% | 微降，避免标签膨胀 |
| 产品介绍重叠 | 40% | 35% | 降低，后续由 embedding 语义补充 |
| 行业分类匹配 | 25% | 35% | 提高（修复双重计分后行业维变干净，可提升权重） |
| 企业规模相似度 | 0% | 0%（赛道开关） | 仅非医药赛道可选开启，权重 15% |
| 成立年限接近度 | 0% | 0%（赛道开关） | 仅非医药赛道可选开启，权重 10% |

> 注：规模/年限开启时，三维度权重相应缩减（标签 25%、产品 30%、行业 20%）。当某维度数据缺失时，其权重按比例分配给其余维度。

**评审建议**：

- 规模/年限维度作**软惩罚**（降权），不做硬过滤；仅在目标与候选**双方均有可靠数据**时启用。
- 体量和年限假设并非普适：Biotech/SaaS 等赛道存在「初创 vs 巨头仍争同一客户」的情况，须在黄金集上验证是否伤害召回。
- 规模/年限**不能替代** embedding 语义召回；bigram 漏判问题仍须靠下一阶段向量检索解决。

**涉及文件**：
- `server/utils/competitor-analysis/competitorAnalysisRunner.js` — `ruleScoreCandidate()` 函数
- `server/utils/competitor-analysis/competitorMatchUtils.js` — 新增 `scaleSimilarity()`、`ageSimilarity()` 函数

### 优化项 2：S3 保持轻量，维度评估统一到 S5

**目标**：避免 S3/S5 两阶段重复判断和 token 成本翻倍。S3 维持轻量对标，结构化维度评估和竞品类型分类统一在 S5 一次调用中完成。

**修订理由**：

原方案让 S3 输出 7 个维度子分（dimension_scores），但同时明确说这些子分"可选写入，供调试，不作为落库门槛"——用户永远看不到这些字段，但每次分析都要为它们付出 token 成本。S3 候选池最大 39 个，Prompt 变长后单次 token 显著上升。更根本的问题是 S3 和 S5 都在做"竞品判断"，两阶段的判断维度大量重叠（客户重合度、场景重合度、替代性等），但又说"以 S5 为准"——如果 S5 是权威，S3 的维度评估就是冗余判断。

**具体改动**：

S3（`PROMPTS.pair_similarity`）**维持现状**，仅输出 `similarity_score` + `rationale`。不做 Prompt 变更，不增加输出字段。

七维度评估（客户重合度、场景重合度、替代性、技术路线、商业模式、发展阶段、市场重合度）**移至 S5**，与竞品类型分类在同一次 LLM 调用中完成（见优化项 3）。

**中长期演进**：对已进入校验池的候选评估**合并 S3+S5 为单次结构化调用**，或由 reranker 替代 S3 轻量对标。此演进依赖 embedding POC 结果。

**涉及文件**：

- `server/utils/competitor-analysis/competitorAnalysisAi.js` — `PROMPTS.pair_similarity` **不改动**
- `server/utils/competitor-analysis/competitorAnalysisRunner.js` — S3 结果解析**不改动**

### 优化项 3：优化 S5 校验 Prompt，承担完整结构化输出

**目标**：S5 校验阶段承担竞品类型分类 + 七维度评估 + 核心差异 + 证据来源声明，成为唯一的落库权威判断层。

**具体改动**：

将 `PROMPTS.validate` 的输出结构扩展为：

```
你是企业竞品校验助手。根据目标企业与候选企业的信息，完成以下判断：

一、竞品类型分类（六选一）：
- direct：同客户、同场景、同预算，客户通常二选一
- indirect：解决同一需求，但产品形态或路线不同
- substitute：非同类产品，但替代客户预算或使用路径
- upstream_downstream：供应链/渠道/能力互补关系
- same_track：概念或行业相近，但不构成实质竞争
- not_competitor：文本或标签相似，业务实质不相关

二、七维度评估（各 0-100）：
1. customer_overlap：目标客户重合度（大企业/中小企业/政府/消费者/医院/学校/开发者等）
2. scenario_overlap：使用场景重合度（是否解决同一个工作流或业务场景）
3. substitutability：产品/方案替代性（客户是否会在采购、预算或使用路径上二选一）
4. tech_similarity：技术路线相似度（是否采用相近技术路线）
5. biz_model_similarity：商业模式相似度（是否同为SaaS/API/硬件销售/项目制/平台抽佣等）
6. stage_relevance：发展阶段相关性（融资轮次、客户规模、产品成熟度是否可比）
7. market_overlap：市场重合度（是否在同一区域/行业垂直市场竞争）

三、综合判断：
- is_competitor：是否构成竞品关系
- validated_score：校验综合分（0-100）

仅输出 JSON：
{
  "is_competitor": true/false,
  "competitor_type": "direct|indirect|substitute|upstream_downstream|same_track|not_competitor",
  "is_listed": true/false,
  "industry_match": true/false,
  "core_overlap_percent": 0-100,
  "is_upstream_downstream": true/false,
  "validated_score": 0-100,
  "reject_reason": "",
  "key_differences": "核心差异一句话",
  "dimension_scores": {
    "customer_overlap": 0-100,
    "scenario_overlap": 0-100,
    "substitutability": 0-100,
    "tech_similarity": 0-100,
    "biz_model_similarity": 0-100,
    "stage_relevance": 0-100,
    "market_overlap": 0-100
  },
  "rationale": "竞品判断一句话总结"
}
禁止 Markdown 与 JSON 外文字。
```

**竞品类型枚举**（来自 PDF 建议）：

| 类型 | 含义 | 系统处理 |
|------|------|----------|
| `direct` | 同客户、同场景、同预算，客户通常二选一 | 保留，高优先级展示 |
| `indirect` | 解决同一需求，但产品形态或路线不同 | 保留，中优先级展示 |
| `substitute` | 非同类产品，但替代客户预算或使用路径 | 保留，低优先级展示 |
| `upstream_downstream` | 供应链/渠道/能力互补关系 | 排除（与现有逻辑一致） |
| `same_track` | 概念或行业相近，但不构成实质竞争 | 落库但 `include_in_comparable = 0`，前端默认隐藏 |
| `not_competitor` | 文本或标签相似，业务实质不相关 | 排除 |

**落库策略（已确定）**：

| 类型 | 是否落库 | include_in_comparable | 说明 |
|------|----------|-----------------------|------|
| `direct` / `indirect` | 是 | 1 | 按现有综合分阈值；`direct` 可优先展示 |
| `substitute` | 是 | 1 | 低优先级展示；阈值可略放宽展示、不放宽告警 |
| `same_track` | 是 | **0** | 综合分达标则落库，但默认不进入可比公司列表；前端可切换查看 |
| `upstream_downstream` / `not_competitor` | 否 | — | 与现有排除逻辑一致 |

> `include_in_comparable` 字段已存在于 `sourcing_competitor_relation` 表（`TINYINT(1) DEFAULT 0`）。`same_track` 类型落库时设为 0，前端默认筛选 `include_in_comparable = 1`，用户可切换查看全部。

S5 输出增加 `key_differences`（核心差异一句话）和 `rationale`（竞品判断一句话），写入 `evidence_summary` 合并展示。

**涉及文件**：
- `server/utils/competitor-analysis/competitorAnalysisAi.js` — `PROMPTS.validate`
- `server/utils/competitor-analysis/competitorAnalysisRunner.js` — S5 结果解析，新增 `dimension_scores` 存入候选对象
- `client/src/pages/competitor-analysis/` — 前端展示竞品类型标签 + 维度雷达图（可选）

### 优化项 4：标签级排除机制

**目标**：允许用户在触发竞品分析时指定排除特定行业或标签的企业，避免明显不相关的企业进入候选池。

**修订理由**：

原方案建议用 `ai_product_intro`、`ai_industry_tags_display`、`qcc_intro_effective` 做文本关键词匹配排除。问题在于"医疗"这样的词会误杀合法的医疗器械竞品，"CRO"会排除做 CRO 服务的竞争对手。文本关键词匹配过于脆弱，无法区分"排除整个行业"和"排除包含某词的企业"。

**具体改动**：

**4.1 前端：在"触发竞品分析"弹窗中增加"排除标签"选择器**

用户可选择排除特定 `industry_l1`（如"消费品"、"房地产"）或特定 tag（如"CDMO"、"CRO"——仅当用户明确要排除纯 CDMO 服务商而非将 CDMO 作为能力的企业时）。选择器从已有标签体系中拉取，而非自由文本输入。

**4.2 后端：S2 规则打分后增加标签级排除**

在 `ruleScoreCandidate()` 打分完成后，检查候选的 `industry_l1`、`industry_l2`、`ai_industry_tags_display`、`ai_industry_tags_json` 是否命中排除标签。命中则标记 `excluded: true`，不进入 LLM 池。

```javascript
function applyExclusionFilter(candidates, exclusionConfig) {
  const { excludeIndustryL1 = [], excludeTags = [] } = exclusionConfig;
  for (const c of candidates) {
    const hitIndustry = excludeIndustryL1.length > 0
      && excludeIndustryL1.includes(c.industry_l1);
    const candidateTags = c.ai_tags_json || [];
    const hitTag = excludeTags.length > 0
      && excludeTags.some(t => candidateTags.includes(t));
    if (hitIndustry || hitTag) {
      c.excluded = true;
      c.exclusion_reason = hitIndustry ? 'industry_l1' : 'tag';
    }
  }
  return candidates;
}
```

**4.3 持久化排除配置**

将用户的排除配置存入主体级配置表 `competitor_analysis_subject_config`（`subject_type` + `subject_id` + `exclusion_industry_l1` + `exclusion_tags`），覆盖投前+被投主体。

**4.4 S5 兜底（可选增强）**

对于用户以自然语言描述的排除意图（如"不要召回纯渠道商"），可将其作为 `exclusion_description` 传入 S5 validate Prompt，让 LLM 在校验时判断是否属于排除类别。这比 S2 阶段的文本匹配可靠得多，但作为兜底而非主排除路径。

**涉及文件**：
- `server/utils/competitor-analysis/competitorAnalysisRunner.js` — 新增 `applyExclusionFilter()`
- `server/routes/competitor-analysis/competitorMatchRoutes.js` — 接受排除参数
- `client/src/pages/competitor-analysis/` — 触发分析的 UI 增加标签选择器

### 优化项 5：动态调整分数融合权重（P2，须先做数据分布分析）

**目标**：当前有内部来源时固定 `internal * 0.6 + AI * 0.4`，若内部数据质量不高（如 `ai_product_intro` 写得笼统或极短），60% 的权重反而拖后腿。

**修订理由**：

原方案的 `estimateDataQuality()` 仅检查简介长度和标签数量，无法区分"长但空洞"与"短但精准"。且与现有逻辑（无内部源→ai_only、AI≥80→2:8、默认→6:4）叠加后产生四条路径，复杂度爆炸，方案也未给出统一设计。须先收集实际数据分布，确认是否真有足够的数据质量差异需要动态权重，再做统一设计。

**前置条件（P2 启动前必须完成）**：

1. **数据分布分析**：统计现有候选中 `ai_product_intro` 长度、标签数量、industry 字段完整度的实际分布，确认是否存在显著的数据质量分层。
2. **统一设计**：将三条现有路径与新动态权重合并为单一公式：`internalWeight = f(dataQuality, aiConfidence)`，其中 `aiConfidence` 高时自动降低 internal 权重（与现有 2:8 路径合并），`dataQuality` 低时也降低 internal 权重。两个因子叠加，而非两套独立规则。

**具体改动（P2 确认前置条件后实施）**：

```javascript
function estimateDataQuality(c) {
  // 须基于实际数据分布分析结果调优阈值
  const intro = String(c.product_intro || c.qcc_intro_effective || '');
  const tags = c.tags || [];
  let quality = 0;
  if (intro.length >= 50) quality += 0.4;
  else if (intro.length >= 20) quality += 0.2;
  if (tags.length >= 5) quality += 0.3;
  else if (tags.length >= 2) quality += 0.15;
  if (c.industry_std_lv1) quality += 0.3;
  return Math.min(1, quality);
}
```

统一融合公式（替代现有三条路径）：

```
quality = estimateDataQuality(c)
aiConfidence = ai / 100   // AI 分归一化
// 两个因子叠加：AI 越高、数据质量越低 → internal 权重越低
internalWeight = 0.6 * quality * (1 - aiConfidence * 0.6)   // 范围约 0 ~ 0.6
aiWeight = 1 - internalWeight
comprehensive = internal * internalWeight + ai * aiWeight
```

数据质量越高且 AI 分越低，内部规则分权重越大；数据稀疏或 AI 高置信时更多依赖 LLM 判断。此公式在 `quality=1, ai<80` 时退化为接近 6:4，在 `ai≥80` 时自动降低 internal 权重（替代 2:8 路径），在 `quality=0` 时退化为接近 ai_only。

**评审建议**：

- `estimateDataQuality()` 初版仅看简介长度与标签数量，后续应纳入：企查查有效文本长度、行业字段是否齐全、融资/上市信息等（对齐 PDF「字段完整度评分」）。
- 阈值须基于黄金评测集分布调优，不宜拍脑袋常量。

**涉及文件**：
- `server/utils/competitor-analysis/competitorMatchUtils.js` — 新增 `estimateDataQuality()`，修改 `computeComprehensiveScore()`

### 优化项 7：证据可信度——系统计算而非 LLM 自评

**目标**：避免 LLM 幻觉，要求每条竞品结论有可追溯的证据来源。证据可信度由系统根据来源级别 + 多源一致性自动计算，而非由 LLM 自评。

**修订理由**：

原方案让 LLM 自己给自己的证据可信度打分（`evidence_confidence` 字段由 LLM 输出）。这是循环论证——幻觉的 LLM 同样会给自己高置信度。PDF 正确指出证据可信度应来自"来源级别 + 新鲜度 + 多源一致性"。因此改为系统根据 `evidence_sources` 自动计算。

**具体改动**：

**7.1 证据来源记录（evidence_sources，P1）**

在 S5 落库时，系统根据候选数据来源自动填充 `evidence_sources`（JSON 数组），记录依据类型：

| 来源类型 | 说明 | 判定条件 |
|----------|------|----------|
| `qcc` | 企查查业务介绍 | 候选有 `qcc_intro_effective` 且非空 |
| `internal_project` | 底层项目库 | 候选来自内部项目库匹配 |
| `internal_financing` | 融资事件库 | 候选来自融资事件匹配 |
| `ai_web` | 联网发现 | 候选来自 S4 web discovery |
| `llm_inference` | 无外部文本、纯模型推断 | 候选无上述任何来源数据，S5 判断基于 LLM 自身知识 |

**7.2 证据可信度系统计算（evidence_confidence，P2.1 多维加权）**

> **修订（2026-06-24）**：P2 MVP 仅按「来源个数」打高/中/低，会把**滞后的企查查/底层/融资描述**误判为「高」。可信度应拆为三个正交维度，再加 S5 判断强度辅助，加权合成总分。

**7.2.1 三个正交维度（落库写入 `evidence_breakdown_json`）**

| 维度 | 字段 | 含义 | 主要信号 |
|------|------|------|----------|
| 来源覆盖 | `source_coverage_score` | 有没有外部依据 | `evidence_sources` 类型与个数；`user_added` 上限 95 |
| 数据新鲜度 | `freshness_score` | 描述是否可能过期 | 候选 `event_date`（底层 `biz_update_time` / 融资 `event_date`）；无日期默认 40 |
| 多源一致性 | `consistency_score` | 多源文本是否互相印证 | `product_intro` vs `qcc_intro` 的 `textOverlapScore`；严重矛盾 → ≤25 |
| 判断强度（辅助） | `judgment_strength_score` | 在现有文本下 S5 结论有多强 | `validated_score` 或 `dimension_scores` 均值；**不替代新鲜度** |

**新鲜度分段（`freshness_score`）**——取候选各来源中**最新** `event_date`：

| 距今天数 | 分数 |
|----------|------|
| ≤12 个月 | 100 |
| 12–24 个月 | 80 |
| 24–36 个月 | 60 |
| >36 个月或无日期 | 40 |

**来源覆盖（`source_coverage_score`）**：

| 条件 | 分数 |
|------|------|
| 含 `user_added` | 95 |
| ≥2 种外部来源（非 `llm_inference`） | 80 |
| 1 种外部来源 | 55 |
| 仅 `llm_inference` | 20 |

**多源一致性（`consistency_score`）**：

- 有 `product_intro` 与 `qcc_intro`：\(40 + \text{textOverlap} \times 60\)
- 重叠 &lt;0.15 且两段均 ≥20 字：视为矛盾，**25**
- 仅单段文本：中性 **55**

**7.2.2 加权合成与封顶规则**

```javascript
const WEIGHTS = { source: 0.35, freshness: 0.30, consistency: 0.25, judgment: 0.10 };

// 仅 llm_inference → 固定 30，needs_review=1
// 否则：
evidence_confidence = round(
  source_coverage * 0.35 +
  freshness * 0.30 +
  consistency * 0.25 +
  judgment_strength * 0.10
);
// 封顶：freshness≤40 → 总分上限 70；多源且 consistency<35 → 总分上限 55
```

**7.2.3 待复核（needs_review，D4-B）**

满足任一即 `needs_review = 1`（仍允许落库）：

- `evidence_confidence < 60`
- `consistency_score < 35`（多源矛盾）
- `freshness_score ≤ 40` 且 `source_coverage_score < 70`（陈旧单源）

**7.2.4 前端展示**

- 列「证据可信」：高（≥80）/ 中（60–79）/ 低（&lt;60）+ 「待复核」标签
- Tooltip 展示四维子分：`来源 xx | 新鲜度 xx | 一致性 xx | 判断强度 xx`，避免单一标签误导

**7.2.5 后续路线（非本期）**

- 黄金集标注「描述是否过时」反推衰减系数
- 投资经理反馈闭环调权重
- Embedding 语义一致性；联网 URL 抓取时间

**自动落库约束（D4-B，不变）**：仅 `llm_inference` 标低可信 + 待复核，**不禁止**自动落库。

**7.3 复核闭环（P2.2，2026-06-24）**

| 字段 | 说明 |
|------|------|
| `review_status` | `pending` / `confirmed` / `dismissed` / `corrected` |
| `review_disposition` | 最近处置：`confirm` / `reject_not_competitor` / `corrected` / `refresh_evidence` |
| `reviewed_by_user_id` / `reviewed_at` / `review_note` | 人工留痕 |
| `human_locked` | 1 = 重跑不软删、不重复落库 |

**API**：`PATCH /competitor-analysis/relations/:id/review`  
确认竞品时须传 `evidence_confidence_tier`：`high`(85) / `medium`(65) / `low`(45)，写入 `human_confirmed_evidence_tier`。

**前端**：竞品明细「复核」抽屉（确认 / 修正类型 / 非竞品 / 刷新证据）+ 待复核筛选。

**7.4 证据摘要（evidence_summary，P1）**

在 `sourcing_competitor_relation` 表新增字段 `evidence_summary`（TEXT），合并 S5 输出的 `rationale` + `key_differences`，记录 LLM 判断的关键依据，如：

> "目标企业做抗体药物CDMO，候选企业同为抗体CDMO且客户群重叠（均服务创新药企），技术路线均为CHO细胞表达平台。核心差异：候选仅服务早期客户，目标已覆盖商业化阶段。"

**7.5 前端展示证据**

在竞品关系表中显示：证据摘要 + 数据源标签 + **证据可信（含 Tooltip 四维子分）** + 待复核标识。

**涉及文件**：
- `server/utils/competitor-analysis/competitorEvidenceUtils.js` — 多维 `evidence_confidence` + `evidence_breakdown_json`
- `server/utils/competitor-analysis/competitorAnalysisRunner.js` — 落库时写入 `evidence_sources` + `evidence_summary` + 可信度字段

### 优化项 8：阈值参数化——投前/投后差异化（P0，1-2 行改动）

**目标**：当前落库阈值（60/55/45）对所有主体统一，但投前查重需要高召回（宁可多候选），投后监控需要低噪音。系统已支持 `subject_type`（`invested_enterprise` vs `pre_investment_project`），阈值应按场景区分。

**具体改动**：

在 `competitorMatchUtils.js` 中将常量改为按 `subject_type` 读取：

```javascript
const THRESHOLDS = {
  invested_enterprise: {
    PERSIST: 60,      // 投后：维持现有阈值，低噪音
    HIGH_LLM: 55,
    VALIDATE_MIN: 45,
  },
  pre_investment_project: {
    PERSIST: 55,      // 投前：降低5分，偏向高召回
    HIGH_LLM: 50,
    VALIDATE_MIN: 40,
  },
};

function getThresholds(subjectType) {
  return THRESHOLDS[subjectType] || THRESHOLDS.invested_enterprise;
}
```

`meetsPersistThreshold()` 和 `buildValidatePool()` 中的阈值从 `subjectType` 上下文获取。

**涉及文件**：
- `server/utils/competitor-analysis/competitorMatchUtils.js` — 阈值改为按 `subject_type` 读取
- `server/utils/competitor-analysis/competitorAnalysisRunner.js` — 传递 `subjectType` 上下文

## 六、风险评估

### 6.1 已识别风险

1. **LLM Prompt 变更导致输出不稳定**：S5 Prompt 扩展为七维度 + 竞品类型，输出字段增多，需要测试不同模型的输出一致性；**必须**在黄金评测集 smoke test（5～10 个）上验证后再全量推广。
2. **竞品类型枚举扩展**：初期六种类型可能不够，预留扩展空间（VARCHAR 而非 ENUM）。
3. **动态权重引入不确定性**：`estimateDataQuality()` 的阈值需要基于实际数据分布调优；须与现有三条路径统一设计，避免规则冲突。（P2，须先完成数据分布分析）
4. **标签排除误杀**：用户配置的排除标签可能过于宽泛；UI 须提供命中预览（展示将被排除的候选数量），并提示"仅排除明显不相关的领域"。
5. **架构局部最优**：仅改 Prompt/规则而不补语义召回，**漏召**（话术不同、业务相似）问题长期存在；规模/年限软惩罚无法替代 embedding。
6. **规模/年限 heuristic 误伤召回**：Biotech、SaaS 等赛道「初创 vs 巨头」「老厂转型 vs 新创」仍可能构成竞争；已限制为按赛道开关且医药赛道默认关闭，但仍须在黄金集上验证。
7. **标签双重计分未修则权重调整失效**：`industry_l1` 缺失时的 tag 回退逻辑不修复，调低 tag 权重仍无法消除重复计分。（P0 优先修复）
8. **投前阈值降低引入噪音**：投前场景降低阈值 5 分以提升召回，可能引入更多非竞品；须在黄金集上验证 precision 是否可接受。
9. **成本与延迟**：S5 Prompt 扩展后单次 token 上升；S3 维持轻量不变。须监控单主体 LLM 调用次数与耗时，必要时缩小 S5 校验池大小（当前 TOP_N_VALIDATE + 15 = 39）。
10. **缺乏反馈闭环**：无投资经理确认回写，阈值与 Prompt 无法持续校准，重复 PDF 警告的「经验常量」困境。（P3 反馈闭环解决）
11. **增量重分析冲突**：用户重新触发竞品分析时，可能覆盖已人工确认的结果；须实现增量重分析逻辑（保留已确认记录，仅重算未确认部分）。（P3）

### 6.2 风险缓解措施

- **S5 Prompt 扩展风险**：先在 5-10 个 smoke test 上验证输出稳定性，确认 JSON 格式合规率和维度评分一致性后再全量推广。
- **阈值参数化风险**：投前阈值降低幅度（5 分）可配置，初始可先不变（等于投后），待黄金集验证后再调整。
- **标签排除风险**：排除操作为 S2 阶段软过滤（标记 excluded 而非物理删除），用户可在结果中查看被排除的候选，支持撤销。
- **evidence_confidence 系统计算风险**：初版来源分级规则较粗（多源 85 / 单源 65 / 纯推断 30），后续可根据实际数据调整分级阈值。

## 七、修订版方案（2026-06-23，基于代码评审）

> 在 §二 原优化项基础上收敛：补齐实现层缺口、降低 S5 Prompt 复杂度、明确分步交付边界。  
> **您确认「做第 N 步」后再启动该步开发**；各步可独立验收。

### 7.1 相对原方案的主要调整
